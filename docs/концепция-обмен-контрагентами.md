# Концепция и приёмка: обмен контрагентами Портал Корп ↔ 1С

**Аудитория:** заказчик / владелец продукта  
**Дата:** 1 ноября 2026  
**Связанные документы:** задание порталу, инструкции администратора РФ и КЗ, OpenSpec `counterparty-exchange-from-tz`

## 1. Зачем

Портал передаёт в бухгалтерию актуальный полный снимок контрагента. Базы РФ и Казахстана принимают его независимо и отвечают статусом обработки. Бухгалтер не запускает обмен вручную: поток идёт через Kafka и фоновые задания расширения `ИнтеграцияApacheKafka`.

## 2. Что входит

| Есть | Нет в этом этапе |
| --- | --- |
| События `contragent_created` и `contragent_updated` | Счета, реализации, поступления |
| Полный снимок: карточка, контакты, адреса, банковские счета, договоры | Номенклатура |
| Два контура: РФ (`organization-id=1`) и КЗ (`organization-id=5`) | Двусторонняя синхронизация правок из 1С на портал |
| Статусы Started → Completed / Failed в `contragents.exchange` | Автосоздание организации или головного контрагента |

## 3. Как устроен поток

1. Портал публикует снимок в топик `contragents`.
2. Каждая база читает своей consumer group (`dev/test/prod.1c.bp.rf` или `…kz`).
3. Код `organization-id` выбирает контур; без заголовка сообщение принимают оба контура.
4. Контур сначала публикует `contragent_exchange_started`, затем применяет снимок и публикует ровно один конечный статус: Completed или Failed.
5. Статусы разных контуров независимы: успех РФ не означает успех КЗ.

Технически 1С подключается к Kafka внешней компонентой Simple Kafka 1C. REST-мост не используется.

## 4. Правила, важные для бизнеса

### Полный снимок

Каждое сообщение — актуальная полная картина контрагента. Банковские счета и договоры, которых нет в новом снимке, **удаляются**, в том числе созданные вручную в 1С. Перед включением на рабочей базе нужны резервная копия и понимание этого правила.

### Идемпотентность

Повтор того же `id` сообщения не создаёт вторую карточку и не запускает второй жизненный цикл статусов.

### Головной контрагент

Если указан `head_contragent`, но головы ещё нет в базе, контур ждёт до трёх попыток. После исчерпания — Failed с кодом `HEAD_CONTRAGENT_NOT_FOUND`.

### Организация в договоре

`contracts[].organization.uid` — GUID существующей организации в целевой базе 1С. Организация обменом не создаётся.

### Версия контракта

Поддерживается major `1` (allow-list вида `1.0.*`). Поле `revision` в контракт не входит: порядок держит Kafka key (`uid`, иначе строковый `id`).

## 5. Риски и как их закрывают

| Риск | Мера |
| --- | --- |
| Удаление ручных счетов и договоров | Аудит предыдущего снимка, резервная копия до включения, явная приёмка сценария удаления |
| Разный результат РФ и КЗ на одном сообщении | Независимые статусы; портал обрабатывает оба ответа по `correlation-id` |
| Дубли карточек по ИНН/КПП или внешним ключам | Код `DUPLICATE_CONFLICT`, данные не меняются |
| Нельзя удалить используемый договор/счёт | Откат всей транзакции, `INTERNAL_ERROR` |
| Повтор после терминальной ошибки | Только явный replay администратора |

## 6. Критерии приёмки

Минимальный набор для закрытия этапа:

1. Сообщение с `organization-id=1` создаёт/обновляет карточку в базе РФ; в `contragents.exchange` есть Started и Completed (или корректный Failed).
2. Сообщение с `organization-id=5` аналогично отрабатывает в базе КЗ.
3. Сообщение без `organization-id` обрабатывается обоими контурами независимо.
4. Повтор того же message `id` не создаёт вторую карточку.
5. Неверный снимок даёт Failed с массивом `messages[]` из каталога кодов ошибок.
6. Отсутствие счёта/договора в новом снимке удаляет его в 1С; запрет удаления откатывает всю операцию.
7. Администратор может остановить/запустить consumer, посмотреть диагностику и выполнить явный replay failed.

Протоколы технических прогонов хранятся в `build/verification/` репозитория разработки и в OpenSpec `tasks.md`.
