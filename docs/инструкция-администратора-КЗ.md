# Обмен контрагентами с порталом: инструкция администратора (БП КЗ)

**Обновлено:** 11.11.2026
**Для кого:** администратор 1С, который устанавливает и сопровождает обмен в «Бухгалтерии для Казахстана».
**Что нужно уметь:** работать в Конфигураторе и в режиме «Все функции», выдавать роли пользователям.
**Для базы РФ** есть отдельная инструкция: [инструкция-администратора-РФ.md](инструкция-администратора-РФ.md). Устроены они одинаково, отличаются значения настроек.

Паролей в документе нет. Где хранится пароль Kafka, сказано в шаге 3.

---

## 1. Как работает обмен

Обмен идёт через два топика Kafka:

- **`contragents`**: в нём передаются карточки контрагентов, в обе стороны;
- **`contragents.exchange`**: в нём передаются статусы обработки карточек.

Есть два встречных потока.

**Портал → 1С.** Портал присылает карточку контрагента целиком: реквизиты, адреса, банковские счета, договоры. 1С находит карточку у себя или создаёт новую. Затем 1С отвечает статусами: «взял в работу», потом «готово» или «ошибка».

**1С → портал.** Бухгалтер заводит нового контрагента в 1С. Через 5 минут 1С отправляет карточку на портал. Пауза нужна, чтобы бухгалтер успел добавить счёт и договор. Портал отвечает статусами. Затем портал присылает обратно ту же карточку уже со своими номерами, и 1С связывает их со своей карточкой.

Главное правило: **1С только создаёт контрагента, дальше хозяин карточки — портал.** Правки карточки в 1С на портал не уходят.

### Чем база КЗ отличается от базы РФ

| | База КЗ | База РФ |
|---|---|---|
| Файл расширения | `IntegracijaApacheKafka-kz.cfe` | `IntegracijaApacheKafka-rf.cfe` |
| Код контура | `KZ` | `RF` |
| Подпись пакетов (`sender`) | `1c-kz` | `1c-rf` |
| Код организации на портале | `5` | `1` |
| Группы Kafka | `dev.1c.bp.kz`, `dev.1c.bp.kz.exchange` | `dev.1c.bp.rf`, `dev.1c.bp.rf.exchange` |
| Регистрационный номер (`reg_number`) | БИН / ИИН | ИНН |

Топики у обеих баз общие. Файл расширения РФ в базу КЗ не загружается: у баз разные внутренние идентификаторы объектов.

| № | Откуда → куда | Топик | Тип | Пример |

## 2. Что подготовить заранее

| Что | У кого запросить |
|---|---|
| Адрес брокера Kafka (`хост:порт`), логин и пароль | администратор Kafka |
| Созданы топики `contragents` и `contragents.exchange` | администратор Kafka |
| Права: чтение и запись в оба топика, чтение для групп `dev.1c.bp.kz` и `dev.1c.bp.kz.exchange` | администратор Kafka |
| Файл расширения `IntegracijaApacheKafka-kz.cfe` | [GitHub, папка `dist`](https://github.com/DmitrySkrypkin/1c-kafka-counterparties/tree/main/dist) |

## 3. Настройка по шагам

Шаги нужно выполнять по порядку. После каждого шага указано, как проверить результат.

### Шаг 1. Установите расширение

1. Откройте Конфигуратор: **Конфигурация → Расширения конфигурации**.
2. Нажмите **Добавить** и выберите файл `IntegracijaApacheKafka-kz.cfe`.
3. Нажмите **Обновить конфигурацию базы данных** (F7).

**Проверка.** В пользовательском режиме появился раздел **Kafka**.

### Шаг 2. Выдайте роли

| Кому | Роль |
|---|---|
| Пользователь, под которым работают регламентные задания | **(Kafka) Сервис обмена** |
| Администратор, который разбирает ошибки | **(Kafka) Диагностика обмена**: с ней видно полное содержимое пакетов |

Сами по себе эти роли не дают войти в базу. Нужен ещё обычный профиль доступа.

### Шаг 3. Положите пароль Kafka

1С ищет пароль в трёх местах и берёт первое найденное:

1. Переменная среды **`KAFKA_PASSWORD`** на компьютере, где работает 1С. Для клиент-серверной базы это сервер 1С.
2. Текстовый файл. Его путь задаётся переменной среды **`KAFKA_PASSWORD_FILE`**; если переменной нет, используется `C:\Temp\kafka-pass.txt`. В файле одна строка `pass: ваш_пароль`.
3. Безопасное хранилище БСП: владелец `KFK_KafkaBroker`, ключ `Пароль`. Записать туда пароль может только администратор средствами типовой конфигурации, расширение этого сделать не может.

Пароль **не** вписывайте в карточку брокера или в настройки контура.

### Шаг 4. Заведите брокер

**Kafka → Справочники → Брокеры → Создать.**

| Поле | Что вписать |
|---|---|
| Наименование | любое, например `Kafka dev` |
| Адрес брокера | `хост:порт`; если брокеров несколько, через запятую |
| Параметры подключения | параметры безопасности **без пароля**, например `security.protocol = SASL_PLAINTEXT`, `sasl.mechanism = PLAIN`, `sasl.username = …` |

**Проверка.** После записи форма загружает список топиков, и в нём видны `contragents` и `contragents.exchange`.

### Шаг 5. Проверьте настройки контура

Откройте **Kafka → Работа с данными → (Kafka) Настройки контуров**, запись с кодом **KZ**. Если записи нет, она создастся сама при первом запуске консьюмера.

| Поле | Значение | Зачем |
|---|---|---|
| Отправитель | `1c-kz` | так 1С подписывает свои пакеты |
| Группа потребителя | `dev.1c.bp.kz` | группа, которой 1С читает карточки |
| Группа потребителя статусов портала | `dev.1c.bp.kz.exchange` | группа, которой 1С читает статусы портала |
| Топик входящий / Топик статусов | `contragents` / `contragents.exchange` | |
| **Допустимые версии** | **`1.0.*;1.1.*`** | по умолчанию стоит `1.0.*`. С ним ответы портала на карточки из 1С будут отклонены с ошибкой `UNSUPPORTED_VERSION` |
| Исходящий обмен включен | пока **нет** | включается в шаге 10 |
| Задержка отправки секунд | `300` | пауза перед отправкой новой карточки на портал |
| Версия исходящего контракта | `1.1.0` | |

Остальные поля описаны в [Приложении А](#приложение-а-все-поля-настроек-контура).

### Шаг 6. Проверьте маршрутизацию организаций

**Kafka → Работа с данными → (Kafka) Маршрутизация организаций.**

| Код организации | Код контура | Активен | Что делает база КЗ |
|---|---|---|---|
| `5` | `KZ` | да | принимает |
| `1` | `RF` | да | пропускает: пакет для России |

Пакет вовсе без кода организации — это рассылка для всех, база КЗ его принимает. Пакет с кодом, которого нет в таблице, пропускается.

### Шаг 7. Проставьте организациям код портала

Договор из 1С уходит на портал вместе с номером организации на портале. Если у организации номера нет, карточка с таким договором **не отправится**: в «Исходящих снимках» она будет в состоянии «ошибка».

1. Откройте **Все функции → Справочники → Организации** и откройте свою организацию.
2. Если поля **«Внешний ID»** нет на форме, добавьте его: **Ещё → Изменить форму**.
3. Впишите номер организации на портале. Для базы КЗ это обычно `5`.

### Шаг 8. Создайте два консьюмера

**Kafka → Справочники → Консьюмеры → Создать.**

| Поле | Консьюмер карточек | Консьюмер статусов портала |
|---|---|---|
| Наименование | `KZ contragents` | `KZ exchange statuses` |
| Идентификатор | `dev.1c.bp.kz` | `dev.1c.bp.kz.exchange` |
| Брокер | из шага 4 | тот же |
| Топики | `contragents` | `contragents.exchange` |
| Активен | да | да |
| Расписание задания | каждые 30 секунд | каждые 30 секунд |
| Таймаут ожидания сообщений | `500` | `500` |
| Параметры консьюмера | `enable.auto.commit = false` | `enable.auto.commit = false` |

**Идентификатор** должен совпадать с названием группы из шага 5. **Без расписания** регламентное задание мониторинга консьюмер не запустит.

> После копирования базы карточек консьюмеров может не оказаться, тогда их нужно создать заново.

### Шаг 9. Включите регламентные задания

Откройте **Администрирование → Обслуживание → Регламентные операции → Регламентные и фоновые задания**. Можно также через **Kafka → Регламентные задания → (Kafka) Консоль заданий**.

| Задание | Что делает | Расписание | Когда включать |
|---|---|---|---|
| **Задание мониторинга консьюмеров** | запускает консьюмеры и перезапускает упавшие | каждые 30 секунд | сразу |
| **Задание публикации исходящих снимков** | отправляет на портал карточки, заведённые в 1С | каждую минуту | вместе с шагом 10 |
| **Задание очистки хранения** | удаляет старое содержимое пакетов по срокам хранения | раз в сутки, ночью | сразу |

В каждом задании укажите пользователя из шага 2, включите **«Использование»** и задайте расписание.

**Проверка.** Через минуту группы `dev.1c.bp.kz` и `dev.1c.bp.kz.exchange` в Kafka должны быть в состоянии **STABLE**, а отставание (lag) должно уменьшаться до нуля.

> **Файловая база.** Регламентные задания работают, только пока в базе открыт хотя бы один сеанс 1С. Два консьюмера в одном сеансе работают **по очереди**. Подробнее в [§8](#8-ограничения).

### Шаг 10. Включите отправку карточек из 1С на портал

Включайте, когда портал подтвердит, что готов принимать карточки из 1С.

1. В **Настройках контуров** для KZ установите **«Исходящий обмен включен» = да**.
2. Включите **«Задание публикации исходящих снимков»**.

Чтобы выключить отправку, снимите флажок.

### Шаг 11. Проверьте обмен целиком

| Проверка | Как | Что должно получиться |
|---|---|---|
| Приём с портала | Попросите портал прислать тестовую карточку с кодом организации `5` | Карточка появилась в справочнике **Контрагенты**, в поле «Внешний ID» номер с портала. В `contragents.exchange` ушли `started`, затем `completed` |
| Отправка на портал | Заведите тестового контрагента с корректным БИН, добавьте договор с вашей организацией и подождите 5–6 минут | **Все функции → Обработки → (Kafka) Рабочий стол → Исходящие снимки**: состояние сначала «отправлено», затем «завершено» |
| Эхо | Пакет из 1С возвращается в 1С | Второй карточки не появилось |

## 4. Повседневная работа

### 4.1. Где что смотреть

| Вопрос | Где смотреть |
|---|---|
| Ушла ли карточка из 1С на портал | **Все функции → Обработки → (Kafka) Рабочий стол**, вкладка **Исходящие снимки** |
| Что пришло с портала и чем закончилось | **Kafka → Работа с данными → Журнал этапов**: `received` → `started` → `completed` или `failed`. Строка `filtered_out` означает «пакет не для этой базы» |
| Почему пакет с портала не принят | **Исходящие статусы**: у статуса `failed` в содержимом указаны код и поле с ошибкой |
| Испорченные пакеты | **Карантин** |
| Какой была карточка до изменения с портала | **Аудит снимков** |

### 4.2. Состояния карточки, отправленной из 1С

| Состояние | Что значит | Что делать |
|---|---|---|
| ожидает (`pending`) | пауза перед отправкой ещё не прошла | ничего |
| ожидает + текст ошибки | не удалось связаться с Kafka | проверить Kafka; задание повторит отправку само |
| отправлено (`sent`) | пакет в Kafka, ответа портала пока нет | ничего |
| в работе (`started`) | портал принял пакет в работу | ничего |
| завершено (`completed`) | портал завёл карточку | ничего |
| ошибка (`failed`) | портал отказал, или 1С не смогла собрать пакет | исправить причину и нажать **«Повторить отправку»** |
| заменено (`superseded`) | по этой записи уже сделан повтор | смотреть новую запись |

### 4.3. Повторная отправка карточки на портал

**Все функции → Обработки → (Kafka) Рабочий стол → Исходящие снимки**, выделите строку, нажмите **«Повторить отправку»**.

При повторе создаётся **новая** запись с новыми номерами сообщения. Пакет собирается заново из текущей карточки, а старая запись получает состояние «заменено». Повторить одну и ту же запись дважды нельзя. Повтор нужен и тогда, когда счёт или договор добавили после отправки.

### 4.4. Повторная обработка пакета с портала

Если пакет с портала закончился ошибкой, исправьте причину и повторно обработайте тот же пакет: вызов приведён в [Приложении Б](#приложение-б-вызовы-для-интегратора). Сама 1С после окончательной ошибки повторять не будет.

## 5. Как 1С ищет карточку для пакета с портала

1. По **номеру портала**: поле «Внешний ID».
2. По **uid**: поле «Внешний UID», либо внутренний идентификатор карточки, если она пришла из 1С.
3. Только если по номеру и uid ничего не нашлось, 1С ищет по **БИН / ИИН**.

| Ситуация | Результат |
|---|---|
| Нашлась одна карточка | карточка обновляется |
| Ничего не нашлось | создаётся новая карточка |
| Номер портала и uid указывают на разные карточки | ошибка `DUPLICATE_CONFLICT`, ничего не меняется |
| Не нашлось по номеру и uid, а по БИН нашлось несколько карточек | ошибка `DUPLICATE_CONFLICT`. Дубли нужно разобрать вручную |
| Нашлось по uid, а с тем же БИН есть ещё карточки | обновляется найденная по uid |

Счета и договоры, которых нет в пакете с портала, не удаляются. Они получают **пометку удаления**, и если элемент снова придёт в пакете, пометка снимется. Если при записи карточки произошла ошибка, база откатывает всё целиком.

## 6. Примеры пакетов

Все примеры — пакеты из тестового прогона 11.11.2026. Номера и названия в них тестовые. В §6.5 договор показан с организацией: так его отправляет текущая версия расширения.

### 6.1. Заголовки — общие для всех пакетов

| Заголовок | Что значит | Пример |
|---|---|---|
| `sender` | кто отправил: `corp` — портал, `1c-kz` — база КЗ, `1c-rf` — база РФ | `corp` |
| `type` | вид пакета | `contragent_created` |
| `version` | версия формата | `1.1.0` |
| `id` | уникальный номер пакета (UUID). Повтор с тем же `id` второй раз не обрабатывается | `df931f1f-ffc6-4fcb-9062-9ff06019ca8c` |
| `correlation-id` | номер «разговора»: ответы несут тот же номер, что и исходный пакет | `c8c277a0-b6cc-464c-a8fd-81ebefc899cf` |
| `timestamp-ms` | время отправки, Unix-время **в секундах**, ровно 10 цифр | `1794411370` |
| `organization-id` | для какой организации пакет. Если заголовка нет, пакет для всех баз | `5` |

**Ключ сообщения** (key) в топике `contragents` равен `uid` карточки.

<a id="62-портал--1с-новая-карточка"></a>

### 6.2. Портал → 1С: новая карточка

Топик `contragents`. В этом примере нет `organization-id`, поэтому пакет получили обе базы.

```json
headers:
{ "sender": "corp", "type": "contragent_created", "version": "1.1.0",
  "id": "b2000001-0000-4000-8000-000000000020",
  "correlation-id": "b2000001-0000-4000-8000-000000000021",
  "timestamp-ms": "1794411900" }
key: b2000001-0000-4000-8000-0000000000a3
value:
{
  "id": 7700003,
  "uid": "b2000001-0000-4000-8000-0000000000a3",
  "name": "ООО Рассылка ОУТ7 Живой",
  "name_short": "Рассылка ОУТ7",
  "type_entity": "legal",
  "reg_number": "7712997701",
  "kpp": "771201001",
  "is_provider": true,
  "is_client": false,
  "bank_accounts": [],
  "contracts": []
}
```

Значения некоторых полей:

| Поле | Значения |
|---|---|
| `type_entity` | `legal` — юрлицо, `sole_proprietor` — ИП, `physical_person` — физлицо, `legal_outside` — нерезидент |
| `reg_number` | БИН / ИИН; база КЗ проверяет его по правилам Казахстана |
| `addresses[].type` | `actual` — фактический, `legal` — юридический, `postal` — почтовый |
| `contracts[].type` | `realization` — с покупателем, `purchase` — с поставщиком |

### 6.3. Портал → 1С: изменение карточки

Топик `contragents`, `type` = `contragent_updated`. Формат такой же, как у новой карточки. Пакет несёт полный снимок карточки: всё, чего нет в пакете, считается удалённым. Пример приведён в [§6.7](#67-портал--1с-изменение-карточки-и-номера-портала).

<a id="64-1с--портал-статусы-обработки"></a>

### 6.4. 1С → портал: статусы обработки

Топик `contragents.exchange`. На каждый принятый пакет 1С отвечает двумя статусами: сначала `started`, затем `completed` или `failed`. Поле `correlation-id` берётся из пакета портала.

Статусы `started` и `completed` несут короткое тело `{ "id": 7700003, "uid": "b2000001-0000-4000-8000-0000000000a3" }`.

**Ошибка.** Это ответ базы КЗ на российского ИП, пришедшего в рассылке для всех баз:

```json
headers:
{ "sender": "1c-kz", "type": "contragent_exchange_failed", "version": "1.0.0",
  "id": "41c64aac-5a8c-41d3-ad09-5b252cf32723",
  "correlation-id": "b2000001-0000-4000-8000-000000000023",
  "timestamp-ms": "1794411723" }
value:
{
  "id": 7700004,
  "uid": "b2000001-0000-4000-8000-0000000000a4",
  "messages": [
    { "code": "INVALID_FORMAT", "path": "reg_number",
      "message": "Введенный БИН / ИИН некорректен." }
  ]
}
```

Коды ошибок:

| Код | Что случилось | Что делать |
|---|---|---|
| `REQUIRED_FIELD_MISSING` | не заполнено обязательное поле | исправить на портале |
| `INVALID_FORMAT` | неверный формат, например БИН не проходит проверку | исправить на портале. Для чужих карточек в рассылке для всех баз это нормальный исход |
| `REFERENCE_NOT_FOUND` | ссылка на то, чего нет в 1С, например на организацию договора | проверить номер и uid организации, шаг 7 |
| `DUPLICATE_CONFLICT` | несколько подходящих карточек в 1С | разобрать дубли, затем повторить обработку |
| `HEAD_CONTRAGENT_NOT_FOUND` | головной контрагент не найден за 3 попытки | прислать головного, затем повторить обработку |
| `UNSUPPORTED_VERSION` | версия пакета не разрешена | шаг 5 |
| `INTERNAL_ERROR` | ошибка внутри 1С | журнал регистрации; 1С повторит сама до 3 раз |

### 6.8. Что 1С пропускает без ответа

| Пакет | Почему пропущен |
|---|---|
| `organization-id` = `1` или неизвестный код | пакет не для этой базы, в журнале этапов `filtered_out` |
| `sender` = `1c-kz` или `1c-rf` в топике `contragents` | свой пакет или пакет соседней базы |
| Статус в `contragents.exchange` не от `corp` | это статусы баз 1С |
| Статус портала с неизвестным `correlation-id` | 1С такую карточку не отправляла |
| Статус `started`, пришедший после `completed` | старый или повторный статус |
| Пакет с тем же `id`, что уже обработан | повтор |

## 7. Если что-то не работает

| Что видно | Вероятная причина | Что сделать |
|---|---|---|
| Группа в Kafka не STABLE, отставание растёт | консьюмеры не запущены | шаг 9: задание мониторинга включено? У карточек консьюмеров «Активен» и расписание? Для файловой базы: открыт ли сеанс 1С? |
| Карточки читаются, а статусы портала нет | файловая база: консьюмеры работают по очереди | см. [§8](#8-ограничения) |
| Ошибка подключения к Kafka | нет пароля или он неверный | шаг 3 |
| Карточка из 1С не уходит, «ожидает» без ошибки | не включён исходящий обмен или задание публикации | шаг 10 |
| Карточка из 1С в состоянии «ошибка», в тексте `contracts[0].organization` | у договора нет организации или у организации нет «Внешнего ID» | шаг 7, затем «Повторить отправку» |
| `UNSUPPORTED_VERSION` | в «Допустимых версиях» нет `1.1.*` | шаг 5 |
| `INVALID_FORMAT` по `reg_number` на российскую карточку | рассылка для всех баз, а номер не проходит проверку КЗ | ничего, так и задумано |
| `DUPLICATE_CONFLICT` | дубли в справочнике контрагентов | §5 |
| В журнале регистрации предупреждение «Смещение в учёте … расходится со смещением группы …» | позиция чтения в 1С отстала от Kafka | ничего; 1С продолжит читать с позиции Kafka. Пакеты, которые другая база прочитала той же группой, в эту базу не попадут |

<a id="8-ограничения"></a>

## 8. Ограничения

- **Правки из 1С на портал не уходят.** Уходит только новая карточка.
- **Счета и договоры, добавленные позже 5 минут**, в отправленный пакет не попадают. Их нужно отправить кнопкой «Повторить отправку».
- **Файловая база.** В одном сеансе фоновые задания выполняются по очереди. Консьюмер карточек работает непрерывно, поэтому консьюмер статусов может не запуститься совсем. Для рабочей эксплуатации нужна **клиент-серверная база**; на файловой согласуйте способ запуска с разработчиком.
- **Одна группа — одна база.** Группу `dev.1c.bp.kz` должна читать только эта база. Если её читает кто-то ещё, например копия базы, часть пакетов в эту базу не попадёт.
- **Документы** этим обменом не передаются, только контрагенты.
