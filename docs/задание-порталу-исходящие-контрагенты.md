# Задание для команды портала: исходящие контрагенты из 1С

**Аудитория:** команда портала Корп и администраторы Kafka  
**Дата:** 10 ноября 2026  
**Контракт:** OpenSpec `counterparty-exchange-outbound-from-1c`, schema `1.1.0`  
**Машиночитаемые схемы:** `src/cfe/ИнтеграцияApacheKafka/contract/counterparty/1.1.0/`  
**Связанный документ (входящий поток):** архив `counterparty-exchange-from-tz` / `задание-порталу-контрагенты.md` (schema `1.0.0`)

Этот документ описывает **новый** поток: карточка создана бухгалтером в 1С → Kafka → портал. Входящий поток портал → 1С остаётся; каталог схем `1.0.0` не меняется.

Пароли и ключи в документ не входят.

## 1. Решение продукта

| Правило | Смысл |
| --- | --- |
| Вариант A | 1С только **создаёт** контрагента; дальше владельцем становится портал |
| Повторные правки в 1С | На портал **не** уходят |
| Существующие карточки без `uid` | Не выгружаются (массовая выгрузка вне scope) |
| Топики | Те же: `contragents` и `contragents.exchange` |

## 2. Топики и направления (дополнение)

| Топик | Новое направление | Пишет | Читает | Содержимое |
| --- | --- | --- | --- | --- |
| `contragents` | **1С → Портал** (добавлено) | `1c-rf` / `1c-kz` | **новая** consumer group портала | `contragent_created` (снимок из 1С, version `1.1.0`) |
| `contragents` | Портал → 1С (как было) | `corp` | группы 1С `*.1c.bp.rf` / `*.1c.bp.kz` | `contragent_created` / `contragent_updated` (`1.0.*` и `1.1.*`) |
| `contragents.exchange` | Портал → 1С (добавлено) | `corp` | группы 1С `*.1c.bp.rf.exchange` / `*.1c.bp.kz.exchange` | Started / Completed / Failed **на исходящее** из 1С |
| `contragents.exchange` | 1С → Портал (как было) | `1c-rf` / `1c-kz` | группа портала | статусы на **входящие** снимки портала |

Портал обязан читать `contragents` своей отдельной группой и **не** делить её с группами 1С.

## 3. Consumer groups

### 1С (уже есть + новые)

| Окружение | РФ (снимки) | КЗ (снимки) | РФ (статусы портала) | КЗ (статусы портала) |
| --- | --- | --- | --- | --- |
| dev | `dev.1c.bp.rf` | `dev.1c.bp.kz` | `dev.1c.bp.rf.exchange` | `dev.1c.bp.kz.exchange` |
| test | `test.1c.bp.rf` | `test.1c.bp.kz` | `test.1c.bp.rf.exchange` | `test.1c.bp.kz.exchange` |
| prod | `prod.1c.bp.rf` | `prod.1c.bp.kz` | `prod.1c.bp.rf.exchange` | `prod.1c.bp.kz.exchange` |

Группы `*.exchange` читают **только** `contragents.exchange`, чтобы смещения статусов не смешивались со снимками.

### Портал (завести)

| Назначение | Топик | Имя группы |
| --- | --- | --- |
| Приём снимков из 1С | `contragents` | выбирает портал, сообщает команде 1С для ACL |
| Приём статусов 1С на свои снимки | `contragents.exchange` | как в документе входящего потока |

## 4. ACL (минимум, дополнение)

Principal 1С РФ / КЗ (добавить к прежнему):

- **WRITE, DESCRIBE:** `contragents` (исходящий снимок)
- **READ, DESCRIBE:** `contragents.exchange` (статусы портала на исходящие)
- READ на свою группу `*.exchange`

Principal портала (добавить):

- **READ:** `contragents` своей новой группой (сообщения `1c-rf` / `1c-kz`)
- **WRITE:** `contragents.exchange` со `sender=corp` в ответ на исходящие из 1С
- WRITE `contragents` для последующего `contragent_updated` с `id`+`uid` — как раньше

## 5. Что публикует 1С в `contragents`

### Заголовки

| Заголовок | Значение |
| --- | --- |
| `sender` | `1c-rf` или `1c-kz` |
| `organization-id` | `1` (РФ) или `5` (КЗ) — код **своего** контура |
| `type` | `contragent_created` |
| `version` | `1.1.0` |
| `id` | UUID сообщения (стабилен при retry транспорта) |
| `correlation-id` | UUID корреляции (тот же при retry транспорта) |
| `timestamp-ms` | Unix **секунды**, ровно 10 цифр |

### Key

Строка `uid` карточки (GUID ссылки в 1С = `KFK_ВнешнийUID`).

### Тело (schema `1.1.0`)

- Обязателен `uid`; числовой `id` портала **может отсутствовать** (его ещё нет).
- Полный снимок: карточка, контакты, адреса, `bank_accounts`, `contracts`.
- Банковский счёт и договор: достаточно `uid` (без портального `id`).
- Счета/договоры, введённые в пределах задержки отправки (по умолчанию 300 с), попадают в тот же снимок.
- Дети, добавленные **после** отправки, в это сообщение не входят и при полном `updated` портала без них могут получить пометку удаления в 1С (действующее поведение входящего потока).

Пример (валидный fixture): `contract/counterparty/1.1.0/fixtures/valid/onec-full-snapshot.json`.

## 6. Что обязан сделать портал

1. **Принять** `contragent_created` от `1c-rf` / `1c-kz` (не отбрасывать из‑за отсутствия числового `id`).
2. **Хранить** `uid` карточки, каждого счёта и каждого договора из снимка.
3. Выдать портальные числовые `id` и ответить статусами в `contragents.exchange`:
   - `sender` = **`corp`** (статусы `1c-*` 1С для исходящих **игнорирует**);
   - тот же `correlation-id`, что у снимка из 1С;
   - типы: `contragent_exchange_started`, затем `contragent_exchange_completed` или `contragent_exchange_failed` (допускаются короткие алиасы `started` / `completed` / `failed`);
   - при Failed — непустой `messages[]` с кодами из каталога контракта.
4. После успешной обработки опубликовать в `contragents` сообщение `contragent_updated` (`sender=corp`, version `1.0.*` или `1.1.*`) с **`id` + `uid`** на карточке, счетах и договорах — чтобы 1С связала `KFK_ВнешнийID` без дубля карточки.
5. Для рассылки во второй контур: осознанно ставить или **не** ставить `organization-id`. Снимок без `organization-id` принимают оба контура; чужой контур отклонит карточку национальной проверкой (например, российский ИП в КЗ → Failed `INVALID_FORMAT` по `reg_number`) — это принятый исход.

## 7. Ожидаемые Failed в чужом контуре

| Сценарий | Ожидание |
| --- | --- |
| РФ юрлицо (валидный ИНН) без `organization-id` → КЗ | Карточка **создаётся** в КЗ |
| РФ ИП / номер, не проходящий проверку КЗ | Failed `INVALID_FORMAT`, путь `reg_number`, карточка не создаётся |
| Повтор того же message `id` с тем же payload | Бизнес повторно не применяется |
| Статус портала с неизвестным `correlation-id` | 1С тихо пропускает (исходящая очередь не меняется) |

## 8. Идемпотентность и повтор

| Сторона | Правило |
| --- | --- |
| 1С → Kafka | Сбой транспорта: тот же message `id` / `correlation-id` до `sent` |
| Админ 1С «Повторить отправку» | **Новые** message `id` и `correlation-id`; портал обязан начать новый жизненный цикл |
| Портал → 1С статусы | Повтор / более старый статус не откатывает цепочку sent → started → completed или failed |

## 9. Чек-лист готовности портала (исходящие из 1С)

1. Consumer group на `contragents` читает сообщения `sender=1c-rf|1c-kz`, `version=1.1.0`, тело без обязательного `id`.
2. Хранение `uid` карточки / счёта / договора.
3. Ответ `corp` Started → Completed|Failed в `contragents.exchange` с исходным `correlation-id`.
4. Публикация `contragent_updated` с `id`+`uid` на карточке и детях.
5. ACL: READ на `contragents`, WRITE на `contragents.exchange` (+ прежние права).
6. Независимость контуров при broadcast без `organization-id`.
7. Новый цикл при новых message id после админского повтора из 1С.

## 10. Что передать команде 1С

- Имя consumer group портала для чтения `contragents`.
- Подтверждение ACL и partition/retention.
- Готовность принимать `1.1.0` без обязательного `id` при `sender ≠ corp`.
