# Инструкция администратора: обмен контрагентами (контур РФ)

**Last Updated:** 2026-11-01  
**Аудитория:** администратор 1С / интегратор  
**Контур:** Бухгалтерия предприятия РФ + расширение `ИнтеграцияApacheKafka`  
**Связанные артефакты:** [README.md](README.md), [design.md](design.md), [tasks.md](tasks.md), [инструкция-администратора-КЗ.md](инструкция-администратора-КЗ.md)

Пароли и ключи Kafka в этот документ **не входят**. Ниже указано только **куда** их положить.

---

## 1. Что это

Входящий обмен полным снимком контрагента с портала:

| Поток | Топик Kafka | Назначение |
|---|---|---|
| Вход | `contragents` | Полный снимок контрагента |
| Выход статусов | `contragents.exchange` | Логические статусы Started → Completed / Failed |

Реализация живёт в расширении **`ИнтеграцияApacheKafka`** (префикс объектов `KFK_`), контур **RF** (`src/cfe/ИнтеграцияApacheKafka`).  
Контур **KZ** — отдельная поставка `src/cfe_bp_kz/ИнтеграцияApacheKafka` и отдельная инструкция.

Бизнес-запись контрагента на РФ делает адаптер расширения; типовая конфигурация `src/cf` для пилота не правится.

---

## 2. Предпосылки

1. Файловая (или серверная) **база БП РФ** с установленным и подключённым расширением `ИнтеграцияApacheKafka`.
2. В Kafka **явно созданы** топики `contragents` и `contragents.exchange` (в prod — **без** auto-create).
3. Внешняя компонента **Simple Kafka 1C** доступна из общего макета `ОбщийМакет.KFK_Компонента` (подключение в `KFK_Интеграция.ПодключитьКомпонентуКафка`).
4. Роли:
   - **`KFK_СервисОбмена`** («(Kafka) Сервис обмена») — сервисный пользователь фона; метаданные без полного payload в admin API.
   - **`KFK_ДиагностикаОбмена`** («(Kafka) Диагностика обмена») — просмотр Inbox / процесса / Outbox **с полным payload**.
   - Плюс типовые права **входа** в базу (роли KFK сами по себе вход не дают).

## 3. Настройка (пошагово)

### 3.1. Справочник брокеров `KFK_Брокеры`

Меню: **Kafka → Справочники → Брокеры** (синоним зависит от интерфейса; объект `Справочник.KFK_Брокеры`).

1. Создайте элемент: наименование произвольное.
2. Заполните **Адрес брокера** (`hostname:9092` или список).
3. На вкладке **Параметры подключения (SASL, SSL…)** задайте несекретные ключи безопасности (механизм, протокол, пользователь и т.п.).  
   **Пароль Kafka в регистр настроек контура не пишется** — см. §3.4.
4. При необходимости загрузите параметры из файла командой формы («Загрузить настройки из файла»).
5. После записи можно подтянуть список топиков с брокера (форма предлагает подключение).

### 3.2. Регистр `KFK_НастройкиКонтуров` (синоним: «(Kafka) Настройки контуров»)

Меню: **Kafka → Работа с данными** (объект в составе подсистемы) либо список регистра при наличии прав.

При **первом чтении** настроек контура RF код сам создаёт стартовый профиль dev, если записи ещё нет (`KFK_НастройкиКонтуровСервер.ПрочитатьНастройки`). Существующую запись не перезаписывает.

Стартовый профиль **RF**:

| Поле метаданных | Стартовое значение (dev) |
|---|---|
| `КодКонтура` | `RF` |
| `Отправитель` | `1c-rf` |
| `ГруппаПотребителя` | `dev.1c.bp.rf` |
| `ТопикВходящий` | `contragents` |
| `ТопикСтатусов` | `contragents.exchange` |
| `КоличествоВоркеров` (WorkerCount) | `1` |
| `ОжидаемоеЧислоРазделов` (ExpectedPartitions) | `1` |
| `ДопустимыеВерсии` | `1.0.*` |
| `БазоваяЗадержкаСекунд` (baseDelay) | `60` |
| `МаксимальнаяЗадержкаСекунд` (maxDelay) | `120` |
| `РазмерПачки` (batch) | `100` |
| `СрокХраненияВходящихДней` | `30` |
| `СрокХраненияИсходящихДней` | `30` |
| `СрокХраненияАудитаДней` | `90` |
| `ПорогОтставания` | `100` |
| `ПорогВозрастаМинут` | `10` |
| `КритическийПорогМинут` | `15` |
| `АдресПодключения` | пусто (логическое имя/метка, **не пароль**) |

Для test/prod смените `ГруппаПотребителя` на `test.1c.bp.rf` / `prod.1c.bp.rf` (см. design §14). Полей секретов в регистре нет.

`group.id` и sender при слушании берутся из этого регистра, а не из идентификатора элемента справочника консьюмеров.

### 3.3. Регистр `KFK_МаршрутизацияОрганизаций`

Синоним: «(Kafka) Маршрутизация организаций».  
Меню: **Kafka → Работа с данными** (в составе подсистемы; стандартная команда списка регистра).  
Альтернатива: «Все функции» или вызов

`KFK_МаршрутизацияОрганизацийСервер.ОбеспечитьНачальныеЗаписи()` / `ЗаписатьСоответствие(...)`.

Начальные коды (создаются при первом обращении, если отсутствуют):

| `КодОрганизации` | `КодКонтура` | Смысл на базе РФ |
|---|---|---|
| `1` | `RF` | Принимается |
| `5` | `KZ` | На РФ = чужой контур → skip / `filtered_out` |

### 3.4. Секреты Kafka (не в git)

Приоритет чтения (`KFK_СекретыОкруженияСервер.ПрочитатьПарольKafka`):

1. Переменная среды процесса **`KAFKA_PASSWORD`**.
2. Файл из **`KAFKA_PASSWORD_FILE`**, иначе по умолчанию `C:\Temp\kafka-pass.txt`.  
   Формат строки: `pass: …` (также принимается `password=…` или одна строка-пароль).
3. Безопасное хранилище БСП, владелец **`KFK_KafkaBroker`**, ключ `Пароль`.

Запись в хранилище из модуля расширения в safe mode может вернуть `SAFE_MODE_WRITE_BLOCKED`. Сидирование тогда делает код **основной конфигурации** / администратор через БСП (`ОбщегоНазначения.ЗаписатьДанныеВБезопасноеХранилище`), не из расширения.

Проверка без утечки секрета в отчёт:

```bsl
KFK_СекретыОкруженияСервер.ПроверитьГотовностьПодключенияKafka()
```

Ожидается `ok=1` / `ready=1`.

### 3.5. Справочник `KFK_Консьюмеры` и ручное слушание

1. **Kafka → Справочники → Консьюмеры** (`Справочник.KFK_Консьюмеры`).
2. Укажите брокер, топик(и) — минимум `contragents`, флаг **Активен**, расписание (для фона), каталог логов, таймаут.
3. Ручной запуск: в списке команда **«Слушать сообщения»** → открывается обработка **`KFK_Консьюмер`** → команда **«Слушать сообщения»**.

Фоновый lifecycle (автомат без консоли):

- Модуль `KFK_КонсьюмерЖизненныйЦиклСервер`: `Запустить` / `Остановить` / `Состояние` / `ЗапуститьКонтур`.
- Регламент **`KFK_ЗаданиеМониторингаКонсьюмеров`** («Задание мониторинга консьюмеров»), метод `KFK_Интеграция.ЗаданиеМониторингаКонсьюмеров`.
- В метаданных **`Use=false`** — по умолчанию выключено; для автомата нужно включить.
- Форма обработки **`KFK_Консьюмер`** («Слушать») — только peek в таблицу, **без** Inbox / Started / apply / Failed. Бизнес-цикл — только серверный `СлушатьСообщения` (фон).

**Как включить автомат:**

1. Откройте **Kafka → Регламентные задания → Консоль заданий** (`Обработка.KFK_КонсольЗаданий`)  
   **или** типовое администрирование регламентных заданий платформы.
2. Найдите «Задание мониторинга консьюмеров» / `KFK_ЗаданиеМониторингаКонсьюмеров`.
3. Включите **Использование**, расписание (например каждые 30 с).
4. В `KFK_Консьюмеры` — **Активен**, топик `contragents`, **заполненное расписание** на карточке (без него мониторинг пропускает элемент).
5. **Файловая ИБ:** держите открытым хотя бы один сеанс 1С (иначе регламенты/фон не крутятся). На серверной ИБ фон ведёт rphost.
6. Проверка: `KFK_КонсьюмерЖизненныйЦиклСервер.Состояние("RF")` → `active≥1`.

Если брокер не отдаёт list-topics (сеть/ACL), мониторинг берёт `ОжидаемоеЧислоРазделов` из `KFK_НастройкиКонтуров`, чтобы воркер всё равно стартовал.

Остановка фона: `KFK_КонсьюмерЖизненныйЦиклСервер.Остановить("RF")` (или отмена фоновых заданий с ключом `СлушатьСообщения_RF_<group>_0`).

### 3.6. Регламент `KFK_ЗаданиеОчисткиХранения`

Синоним: «Задание очистки хранения». Метод: `KFK_Интеграция.ЗаданиеОчисткиХранения`.  
В метаданных **`Use=false`**. Включается так же, как мониторинг (§3.5).

**Чистит** (по срокам из `KFK_НастройкиКонтуров`, через `KFK_СлужебныеЖурналыСервер.ВыполнитьРегламентнуюОчистку`):

| Область | Объект | Что удаляется / очищается |
|---|---|---|
| Inbox | `KFK_ВходящиеСообщения` | устаревшие сырые входящие |
| Outbox payload | `KFK_ИсходящиеСтатусы` | устаревший payload отправленных статусов |
| Process payload | `KFK_ПроцессыОбмена` | сырой payload терминальных `completed`/`failed` |
| Карантин | `KFK_Карантин` | записи старше срока аудита |
| Аудит | `KFK_АудитСнимков` | записи старше срока аудита |

**Не трогает tombstone процесса:** строка в `KFK_ПроцессыОбмена` с ключом `(КодКонтура, MessageID)`, хешем и terminal-состоянием остаётся (идемпотентность при Kafka replay).

## 4. Ежедневная работа

### 4.1. Запуск / остановка consumer

| Способ | Как |
|---|---|
| Ручной | `KFK_Консьюмеры` → «Слушать сообщения» → обработка `KFK_Консьюмер` |
| Фон | Включить `KFK_ЗаданиеМониторингаКонсьюмеров` + активный консьюмер |
| Программный старт | `KFK_КонсьюмерЖизненныйЦиклСервер.Запустить` / `ЗапуститьКонтур` |
| Остановка | `KFK_КонсьюмерЖизненныйЦиклСервер.Остановить("RF")` или отмена фонового задания по ключу |
| Состояние | `KFK_КонсьюмерЖизненныйЦиклСервер.Состояние("RF")` |

### 4.2. Где смотреть очереди и диагностику

Специальных «красивых» форм админ-дашборда для новых регистров **нет** (стандартные списки регистров + API). Меню: **Kafka → Работа с данными**.

| Что смотреть | Объект | Admin API (`KFK_АдминистрированиеОбменаСервер`) |
|---|---|---|
| Inbox | РС `KFK_ВходящиеСообщения` | `ПросмотретьInbox(Группа, Топик, Раздел, Смещение)` |
| Процессы | РС `KFK_ПроцессыОбмена` | `ПросмотретьПроцесс(КодКонтура, MessageID)` |
| Outbox статусов | РС `KFK_ИсходящиеСтатусы` | `ПросмотретьOutbox(КодКонтура, MessageID, Seq)` — Started обычно seq `10`, terminal `20` |
| Журнал этапов | РС `KFK_ЖурналЭтапов` | этапы `received`, `filtered_out`, `started`, `completed`, `failed`, `error` |
| Карантин | РС `KFK_Карантин` | битый envelope и конфликты ключа |
| Аудит снимков | РС `KFK_АудитСнимков` | до/после для восстановления |
| Смещения | РС `KFK_СмещенияКонсьюмеров` | зафиксированные offset |

Режимы просмотра API: `ordinary` (отказ), `service` (метаданные, payload redacted), `diagnostic` (полный payload). Без явного режима выбирается по ролям сеанса.

Вызов — **консоль кода / внешняя обработка / COM**, не отдельная UI-форма.

### 4.3. Метрики и пороги

```bsl
KFK_АдминистрированиеОбменаСервер.СобратьМетрикиКонтура("RF")
```

В отчёте: глубины Inbox/Outbox, возраст, `retry_count`, `failed_count`, флаги `alert_warn` / `alert_critical` относительно порогов из настроек контура (стартово 100 / 10 / 15).

Расхождение числа partition с `ОжидаемоеЧислоРазделов` даёт предупреждение `partition-mismatch` в плане воркеров, но **не блокирует** старт полезных worker.

### 4.4. Явный replay failed

```bsl
// Тот же message id — сброс terminal для повторной обработки
KFK_АдминистрированиеОбменаСервер.ПовторитьFailed("RF", "<message-id>")

// Новый message id — только с подтверждением
KFK_АдминистрированиеОбменаСервер.ПовторитьFailed("RF", "<old-id>", "<new-id>", Истина)
```

**Предупреждение:** заполненный новый message id при `ПодтвердитьНовыйПроцесс = Истина` создаёт **отдельную бизнес-операцию**. Без подтверждения API вернёт `NEED_CONFIRM_NEW_MESSAGE_ID`. Автоповтор после terminal failed планировщик **не** делает.

### 4.5. Что означают Started → Completed / Failed

Логические статусы в топик `contragents.exchange` (через Outbox):

| Статус | Когда | Смысл |
|---|---|---|
| **Started** | После маршрутизации и регистрации процесса, до валидации тела | Контур принял сообщение в работу |
| **Completed** | Успешная запись снимка в 1С | Терминальный успех |
| **Failed** | Терминальная ошибка (или исчерпаны 3 попытки) | Терминальный отказ; в теле — `messages[]` |

Внутренние состояния процесса (`KFK_СостоянияПроцесса`):  
`received` → `started_pending` → `started_sent` → `processing` / `waiting_retry` → `completed` / `failed`.

Бизнес-валидация и запись карточки идут **только после** подтверждённой публикации Started.

## 5. Маршрутизация `organization-id`

Сервис: `KFK_МаршрутизацияОрганизацийСервер.РешениеМаршрута`.

| Заголовок | На контуре RF |
|---|---|
| `1` | Принят (`accepted`) |
| пустой / отсутствует | Широковещание (`broadcast`) — принят |
| `5` | Чужой (`foreign`) → commit offset, этап `filtered_out`, **без** бизнес-статуса в exchange |
| неизвестный / неактивный | `unknown` / `inactive` → то же, что skip без статуса |

## 6. Типовые проблемы

| Симптом | Вероятная причина | Действие |
|---|---|---|
| Статусы не уходят / ошибки публикации | Нет топика `contragents.exchange` | Явно создать топик; в prod отключить auto-create |
| Подключение к брокеру падает, `ready=0` | Нет секрета / неверный источник | Проверить `KAFKA_PASSWORD` → файл → хранилище `KFK_KafkaBroker`; вызвать `ПроверитьГотовностьПодключенияKafka` |
| `DUPLICATE_CONFLICT` | Несколько карточек по id/uid/ИНН+КПП или конфликт организации договора | Разобрать дубли вручную; replay только после исправления данных |
| `HEAD_CONTRAGENT_NOT_FOUND` | Нет головного контрагента после 3 попыток | Создать/привязать голову; затем явный replay failed |
| `SAFE_MODE_WRITE_BLOCKED` | Расширение не может писать в БСП-хранилище | Записать секрет из основной конфигурации / админ-процедуры; или использовать env/файл |
| `partition-mismatch` / лишние worker | `ОжидаемоеЧислоРазделов` ≠ факт на брокере | Сначала изменить Kafka, затем настройку; полезных worker не больше числа partition |
| Consumer не стартует из фона | `KFK_ЗаданиеМониторингаКонсьюмеров` с `Use=false`, консьюмер неактивен, пустое расписание на карточке, или нет сеанса на файловой ИБ | Включить задание, «Активен» + расписание консьюмера; открыть сеанс 1С |
| Ошибка детей уходит как `INTERNAL_ERROR` / `waiting_retry` | Старая сборка адаптера без проброса `REFERENCE_NOT_FOUND` | Обновить `KFK_АдаптерКонтрагентовРФСервер` (ошибки договоров/счетов → terminal Failed) |
| Счёт/договор пропал из снимка, а в ИБ остался | Ожидаемо: ставится `ПометкаУдаления`, физически не удаляется | Проверить пометку на элементе; при возврате в снимке пометка снимается |
| Где смотреть причину Failed | Не в входящем `contragents` | `contragents.exchange` Failed value → `messages[].code/path`; в ИБ — Outbox seq20 `KFK_ИсходящиеСтатусы.Payload` |
| Обычный пользователь не видит payload | Нет роли диагностики | Выдать `KFK_ДиагностикаОбмена` или смотреть в режиме `diagnostic` под своей ролью |

### 7.2. Ручная проверка в консоли кода 1С (тот же сценарий)

1. Убедитесь, что в `KFK_МаршрутизацияОрганизаций` есть активный код `1 → RF`.
2. Скопируйте тело `value` из fixture в строку `ТелоJSON` (или загрузите файл).
3. Выполните цепочку (уникальный `MessageID` на каждый прогон — иначе будет дубль):

```bsl
КодКонтура = "RF";
MessageID = "86613268-0f5f-4c69-b445-2691cdbe7510"; // на повтор — новый UUID
CorrelationID = "5ce6cd28-bec9-45cd-ab8b-e717ac180139";
ТелоJSON = "<вставить value из tz-contragent-created.json>";

Рег = KFK_ПроцессыОбменаСервер.ЗарегистрироватьПроцесс(
	КодКонтура, MessageID, CorrelationID, ТелоJSON);
// Рег.ЭтоДубль = Ложь при первом прогоне

Старт = KFK_ИсходящиеСтатусыСервер.ПодготовитьStarted(КодКонтура, MessageID, "f8f47095-2a07-11ef-abb1-005056a2601e", "");
KFK_ИсходящиеСтатусыСервер.ПодтвердитьДоставкуStarted(КодКонтура, MessageID);

```

4. **Что проверить глазами:**
   - Справочник **Контрагенты**: ИНН `7736035485`, КПП `770801001`, внешний id `111636`, название содержит «СОГАЗ»;
   - банк и договор (по 1 шт.);
   - РС `KFK_ИсходящиеСтатусы`: seq `10` (Started) и `20` (Completed);
   - РС `KFK_ЖурналЭтапов`: `started` → `completed`.

### 7.3. Полный путь через Kafka (если consumer уже настроен)

1. Секрет готов: `KFK_СекретыОкруженияСервер.ПроверитьГотовностьПодключенияKafka()` → `ready=1`.
2. Включите consumer (обработка `KFK_Консьюмер` или фоновое задание).
3. Опубликуйте в топик `contragents` сообщение с headers и value из fixture (`organization-id=1`).
4. Дождитесь появления Started/Completed в `contragents.exchange` и той же карточки в 1С (как в §7.2 п.4).

**Важно:** повтор с тем же header `id` не должен создать вторую карточку — процесс вернёт дубль (`ЭтоДубль`).

## 8. Чего нет (на текущий момент)

- Адаптер контура **KZ** готов отдельной поставкой — см. [инструкцию КЗ](инструкция-администратора-КЗ.md).
- **ACL** Kafka на тестовом кластере — состояние **PARTIAL** (топики созданы вручную; полный прод-ACL не зафиксирован как PASS).
- Адаптер **документов** (счета / реализации / поступления) — **вне** этого change; здесь только контрагенты.
