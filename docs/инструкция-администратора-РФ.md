# Обмен контрагентами с порталом: инструкция администратора (БП РФ)

**Обновлено:** 11.11.2026
**Для кого:** администратор 1С, который устанавливает и сопровождает обмен.
**Что нужно уметь:** работать в Конфигураторе и в режиме «Все функции», выдавать роли пользователям.
**Для базы КЗ** есть отдельная инструкция: [инструкция-администратора-КЗ.md](инструкция-администратора-КЗ.md).

Паролей в документе нет. Где хранится пароль Kafka, сказано в шаге 3.

---

## 1. Как работает обмен

Обмен идёт через два топика Kafka:

- **`contragents`**: в нём передаются карточки контрагентов, в обе стороны;
- **`contragents.exchange`**: в нём передаются статусы обработки карточек.

Есть два встречных потока.

**Портал → 1С.** Портал присылает карточку контрагента целиком: реквизиты, адреса, банковские счета, договоры. 1С находит карточку у себя или создаёт новую. Затем 1С отвечает статусами: «взял в работу», потом «готово» или «ошибка».

**1С → портал.** Бухгалтер заводит нового контрагента в 1С. Через 5 минут 1С отправляет карточку на портал. Пауза нужна, чтобы бухгалтер успел добавить счёт и договор. Портал отвечает статусами. Затем портал присылает обратно ту же карточку уже со своими номерами, и 1С связывает их со своей карточкой.

Главное правило: **1С только создаёт контрагента, дальше хозяин карточки — портал.** Правки карточки в 1С на портал не уходят. Чтобы изменить контрагента, его правят на портале, и изменение приходит в 1С.

### Какие пакеты ходят

| № | Откуда → куда | Топик | Тип | Пример |
|---|---|---|---|---|
| 1 | Портал → 1С | `contragents` | `contragent_created`: новая карточка | [§6.2](#62-портал--1с-новая-карточка) |
| 2 | Портал → 1С | `contragents` | `contragent_updated`: изменение карточки | [§6.3](#63-портал--1с-изменение-карточки) |
| 3 | 1С → портал | `contragents.exchange` | статусы `started` / `completed` / `failed` на пакеты 1 и 2 | [§6.4](#64-1с--портал-статусы-обработки) |
| 4 | 1С → портал | `contragents` | `contragent_created`: карточка, заведённая в 1С | [§6.5](#65-1с--портал-новая-карточка-из-1с) |
| 5 | Портал → 1С | `contragents.exchange` | статусы портала на пакет 4 | [§6.6](#66-портал--1с-статусы-на-карточку-из-1с) |
| 6 | Портал → 1С | `contragents` | `contragent_updated` с номерами портала: ответ на пакет 4 | [§6.7](#67-портал--1с-номера-портала-для-карточки-из-1с) |

## 3. Настройка по шагам

Шаги нужно выполнять по порядку. После каждого шага указано, как проверить результат.

### Шаг 1. Установите расширение

1. Откройте Конфигуратор: **Конфигурация → Расширения конфигурации**.
2. Нажмите **Добавить** и выберите файл `IntegracijaApacheKafka-rf.cfe`.
3. Нажмите **Обновить конфигурацию базы данных** (F7).

**Проверка.** В пользовательском режиме появился раздел **Kafka**.

> Файл расширения КЗ в базу РФ не загружается: у баз разные внутренние идентификаторы объектов.

### Шаг 2. Выдайте роли

| Кому | Роль |
|---|---|
| Пользователь, под которым работают регламентные задания | **(Kafka) Сервис обмена** |
| Администратор, который разбирает ошибки | **(Kafka) Диагностика обмена**: с ней видно полное содержимое пакетов |

Сами по себе эти роли не дают войти в базу. Нужен ещё обычный профиль доступа, например «Администратор».

### Шаг 3. Положите пароль Kafka

1С ищет пароль в трёх местах и берёт первое найденное:

1. Переменная среды **`KAFKA_PASSWORD`** на компьютере, где работает 1С. Для клиент-серверной базы это сервер 1С.
2. Текстовый файл. Его путь задаётся переменной среды **`KAFKA_PASSWORD_FILE`**; если переменной нет, используется `C:\Temp\kafka-pass.txt`. В файле одна строка `pass: ваш_пароль`.
3. Безопасное хранилище БСП: владелец `KFK_KafkaBroker`, ключ `Пароль`. Записать туда пароль может только администратор средствами типовой конфигурации, расширение этого сделать не может.

Пароль **не** вписывайте в карточку брокера или в настройки контура: там его видят все.

### Шаг 4. Заведите брокер

**Kafka → Справочники → Брокеры → Создать.**

| Поле | Что вписать |
|---|---|
| Наименование | любое, например `Kafka dev` |
| Адрес брокера | `хост:порт`; если брокеров несколько, через запятую |
| Параметры подключения | параметры безопасности **без пароля**, например `security.protocol = SASL_PLAINTEXT`, `sasl.mechanism = PLAIN`, `sasl.username = …` |

Запишите карточку. Форма предложит подключиться и загрузить список топиков.

**Проверка.** В списке видны `contragents` и `contragents.exchange`.

### Шаг 5. Проверьте настройки контура

Откройте **Kafka → Работа с данными → (Kafka) Настройки контуров**. Если записи **RF** нет, она создастся сама при первом запуске консьюмера. Её можно добавить и вручную, с кодом контура `RF`.

Почти все поля можно оставить как есть. Проверьте только эти:

| Поле | Значение | Зачем |
|---|---|---|
| Отправитель | `1c-rf` | так 1С подписывает свои пакеты |
| Группа потребителя | `dev.1c.bp.rf` | группа, которой 1С читает карточки |
| Группа потребителя статусов портала | `dev.1c.bp.rf.exchange` | группа, которой 1С читает статусы портала |
| Топик входящий / Топик статусов | `contragents` / `contragents.exchange` | |
| **Допустимые версии** | **`1.0.*;1.1.*`** | по умолчанию стоит `1.0.*`. С ним ответы портала на карточки из 1С (версия 1.1.0) будут отклонены с ошибкой `UNSUPPORTED_VERSION` |
| Исходящий обмен включен | пока **нет** | включается в шаге 10 |
| Задержка отправки секунд | `300` | пауза перед отправкой новой карточки на портал |
| Версия исходящего контракта | `1.1.0` | |

Остальные поля (сроки хранения, пороги, повторы) описаны в [Приложении А](#приложение-а-все-поля-настроек-контура).

### Шаг 6. Проверьте маршрутизацию организаций

**Kafka → Работа с данными → (Kafka) Маршрутизация организаций.**

Портал помечает каждый пакет кодом организации, для которой он предназначен. По этому коду база решает, принимать ли пакет:

| Код организации | Код контура | Активен | Что делает база РФ |
|---|---|---|---|
| `1` | `RF` | да | принимает |
| `5` | `KZ` | да | пропускает: пакет для Казахстана |

Пакет вовсе без кода организации — это рассылка для всех, база РФ его принимает. Пакет с кодом, которого нет в таблице, тоже пропускается. Строки создаются сами при первом обращении. Если их нет, добавьте вручную.

### Шаг 7. Проставьте организациям код портала

Договор из 1С уходит на портал вместе с номером организации на портале. Если у организации номера нет, карточка с таким договором **не отправится**: в «Исходящих снимках» она будет в состоянии «ошибка».

1. Откройте **Все функции → Справочники → Организации** и откройте свою организацию.
2. Если поля **«Внешний ID»** нет на форме, добавьте его: **Ещё → Изменить форму**, отметьте поле «Внешний ID».
3. Впишите номер организации на портале. Для базы РФ это обычно `1`.

### Шаг 8. Создайте два консьюмера

Консьюмер — это карточка «кто и что читает из Kafka». Нужны две карточки: одна читает карточки контрагентов, другая читает статусы портала.

**Kafka → Справочники → Консьюмеры → Создать.**

| Поле | Консьюмер карточек | Консьюмер статусов портала |
|---|---|---|
| Наименование | `RF contragents` | `RF exchange statuses` |
| Идентификатор | `dev.1c.bp.rf` | `dev.1c.bp.rf.exchange` |
| Брокер | из шага 4 | тот же |
| Топики | `contragents` | `contragents.exchange` |
| Активен | да | да |
| Расписание задания | каждые 30 секунд | каждые 30 секунд |
| Таймаут ожидания сообщений | `500` | `500` |
| Параметры консьюмера | `enable.auto.commit = false` | `enable.auto.commit = false` |

**Идентификатор** должен совпадать с названием группы из шага 5, иначе база не свяжет карточку с контуром. **Без расписания** регламентное задание мониторинга консьюмер не запустит.

> Консьюмер статусов можно не заводить вручную. Интегратор создаст его одним вызовом, см. [Приложение Б](#приложение-б-вызовы-для-интегратора).

### Шаг 9. Включите регламентные задания

Откройте **Администрирование → Обслуживание → Регламентные операции → Регламентные и фоновые задания**. Можно также через **Kafka → Регламентные задания → (Kafka) Консоль заданий**.

| Задание | Что делает | Расписание | Когда включать |
|---|---|---|---|
| **Задание мониторинга консьюмеров** | запускает консьюмеры и перезапускает упавшие | каждые 30 секунд | сразу |
| **Задание публикации исходящих снимков** | отправляет на портал карточки, заведённые в 1С | каждую минуту | вместе с шагом 10 |
| **Задание очистки хранения** | удаляет старое содержимое пакетов по срокам хранения | раз в сутки, ночью | сразу |

В каждом задании укажите пользователя из шага 2, включите **«Использование»** и задайте расписание.

**Проверка.** Через минуту откройте Kafbat или спросите администратора Kafka. Группы `dev.1c.bp.rf` и `dev.1c.bp.rf.exchange` должны быть в состоянии **STABLE**, а отставание (lag) должно уменьшаться до нуля.

> **Файловая база.** Регламентные задания работают, только пока в базе открыт хотя бы один сеанс 1С. Кроме того, в одном сеансе два консьюмера работают **по очереди**: пока работает первый, второй ждёт. Подробнее в [§8](#8-ограничения).

### Шаг 10. Включите отправку карточек из 1С на портал

Включайте, когда портал подтвердит, что готов принимать карточки из 1С.

1. В **Настройках контуров** для RF установите **«Исходящий обмен включен» = да**.
2. Включите **«Задание публикации исходящих снимков»** (шаг 9).

Чтобы выключить отправку, снимите флажок «Исходящий обмен включен». Расширение удалять не нужно.

### Шаг 11. Проверьте обмен целиком

| Проверка | Как | Что должно получиться |
|---|---|---|
| Приём с портала | Попросите портал прислать тестовую карточку с кодом организации `1` | Карточка появилась в справочнике **Контрагенты**, в поле «Внешний ID» номер с портала. В `contragents.exchange` ушли `started`, затем `completed` |
| Отправка на портал | Заведите тестового контрагента, добавьте договор с вашей организацией и подождите 5–6 минут | **Все функции → Обработки → (Kafka) Рабочий стол → Исходящие снимки**: состояние сначала «отправлено», затем «завершено». У карточки появился «Внешний ID» с портала |
| Эхо | Пакет из 1С возвращается в 1С, потому что база тоже читает `contragents` | Второй карточки не появилось: свой пакет база пропускает |

## 4. Повседневная работа

### 4.1. Где что смотреть

| Вопрос | Где смотреть |
|---|---|
| Ушла ли карточка из 1С на портал | **Все функции → Обработки → (Kafka) Рабочий стол**, вкладка **Исходящие снимки**: отбор по состоянию, содержимое пакета, ответы портала, ошибка |
| Что пришло с портала и чем закончилось | **Kafka → Работа с данными → Журнал этапов**: `received` → `started` → `completed` или `failed`. Строка `filtered_out` означает «пакет не для этой базы» |
| Почему пакет с портала не принят | **Исходящие статусы**: у статуса `failed` в содержимом указаны код и поле с ошибкой (см. [§6.4](#64-1с--портал-статусы-обработки)) |
| Испорченные пакеты, которые не удалось разобрать | **Карантин** |
| Какой была карточка до изменения с портала | **Аудит снимков**: состояние «до» и «после» |
| Работают ли консьюмеры | состояние групп в Kafbat; в 1С **Kafka → Регламентные задания → Консоль заданий** |

Полное содержимое пакетов видно только пользователю с ролью **(Kafka) Диагностика обмена**.

### 4.2. Состояния карточки, отправленной из 1С

| Состояние | Что значит | Что делать |
|---|---|---|
| ожидает (`pending`) | пауза перед отправкой ещё не прошла | ничего |
| ожидает + текст ошибки | не удалось связаться с Kafka | проверить Kafka; задание повторит отправку само |
| отправлено (`sent`) | пакет в Kafka, ответа портала пока нет | ничего |
| в работе (`started`) | портал принял пакет в работу | ничего |
| завершено (`completed`) | портал завёл карточку | ничего |
| ошибка (`failed`) | портал отказал, или 1С не смогла собрать пакет, например у организации договора нет кода портала | исправить причину и нажать **«Повторить отправку»** |
| заменено (`superseded`) | по этой записи уже сделан повтор | ничего, смотреть новую запись |

### 4.3. Повторная отправка карточки на портал

**Все функции → Обработки → (Kafka) Рабочий стол → Исходящие снимки**, выделите строку, нажмите **«Повторить отправку»**.

Повтор доступен для состояния «ошибка» и для «ожидает» с ошибкой связи. При повторе создаётся **новая** запись с новыми номерами сообщения. Пакет собирается заново из текущей карточки, а старая запись получает состояние «заменено». Повторить одну и ту же запись дважды нельзя.

Повтор нужен и тогда, когда счёт или договор добавили **после** отправки. Сам пакет такие изменения не догоняет.

### 4.4. Повторная обработка пакета с портала

Если пакет с портала закончился ошибкой, исправьте причину, например удалите дубль контрагента. Затем повторно обработайте тот же пакет: вызов приведён в [Приложении Б](#приложение-б-вызовы-для-интегратора). Сама 1С после окончательной ошибки повторять не будет.

<a id="5-как-1с-ищет-карточку-для-пакета-с-портала"></a>

## 5. Как 1С ищет карточку для пакета с портала

1. По **номеру портала**: поле «Внешний ID».
2. По **uid**: поле «Внешний UID», либо внутренний идентификатор карточки, если она пришла из 1С.
3. Только если по номеру и uid ничего не нашлось, 1С ищет по **ИНН + КПП**.

| Ситуация | Результат |
|---|---|
| Нашлась одна карточка | карточка обновляется |
| Ничего не нашлось | создаётся новая карточка |
| Номер портала и uid указывают на **разные** карточки | ошибка `DUPLICATE_CONFLICT`, ничего не меняется |
| Не нашлось по номеру и uid, а по ИНН+КПП нашлось несколько карточек | ошибка `DUPLICATE_CONFLICT`. Дубли нужно разобрать вручную |
| Нашлось по uid, а с тем же ИНН+КПП есть ещё карточки | обновляется найденная по uid, дубли не мешают |

Счета и договоры, которых нет в пакете с портала, не удаляются. Они получают **пометку удаления**. Если элемент снова придёт в пакете, пометка снимется.

Если при записи карточки произошла ошибка, база откатывает всё целиком. Не остаётся ни новой карточки, ни записанных номеров портала.

## 6. Примеры пакетов

Откуда взяты примеры:

- §6.2 и §6.3 — примеры из технического задания;
- §6.4–6.7 — пакеты из тестового прогона 11.11.2026. Номера и названия в них тестовые. Номер портала в §6.6 и §6.7 приведён к одному значению, чтобы цепочку было легче проследить.

### 6.1. Заголовки — общие для всех пакетов

| Заголовок | Что значит | Пример |
|---|---|---|
| `sender` | кто отправил: `corp` — портал, `1c-rf` — база РФ, `1c-kz` — база КЗ | `corp` |
| `type` | вид пакета | `contragent_created` |
| `version` | версия формата | `1.1.0` |
| `id` | уникальный номер пакета (UUID). Повтор с тем же `id` не обрабатывается второй раз | `4baf2094-2c66-4c94-ba08-53425e64936b` |
| `correlation-id` | номер «разговора»: ответы несут тот же номер, что и исходный пакет | `4431e72d-003e-405d-97e8-ce566c0a828d` |
| `timestamp-ms` | время отправки, Unix-время **в секундах**, ровно 10 цифр | `1794408998` |
| `organization-id` | для какой организации пакет. Если заголовка нет, пакет для всех баз | `1` |

**Ключ сообщения** (key) в топике `contragents` равен `uid` карточки.

<a id="64-1с--портал-статусы-обработки"></a>

### 6.4. 1С → портал: статусы обработки

Топик `contragents.exchange`. На каждый принятый пакет 1С отвечает двумя статусами: сначала `started`, затем `completed` или `failed`. Поле `correlation-id` берётся из пакета портала.

**Принят в работу:**

```json
headers:
{ "sender": "1c-rf", "type": "contragent_exchange_started", "version": "1.0.0",
  "id": "a11631a8-e458-40a6-a4dc-50e93993edda",
  "correlation-id": "a1000001-0000-4000-8000-000000000017",
  "timestamp-ms": "1794410359" }
value:
{ "id": 7700001, "uid": "670c8bc6-dddf-11f1-9953-010101010000" }
```

**Готово:** заголовки те же, `type` = `contragent_exchange_completed`, тело такое же.

**Ошибка:**

```json
headers:
{ "sender": "1c-rf", "type": "contragent_exchange_failed", "version": "1.0.0",
  "id": "f94619f0-b2a3-4619-87cb-3ffd7a3ebc33",
  "correlation-id": "b2000001-0000-4000-8000-000000000031",
  "timestamp-ms": "1794412496" }
value:
{
  "id": 7700005,
  "uid": "b2000001-0000-4000-8000-0000000000a5",
  "messages": [
    { "code": "REFERENCE_NOT_FOUND",
      "path": "contracts[0].organization.uid",
      "message": "Не найдена организация с uid b2000001-0000-4000-8000-0000000000c5" }
  ]
}
```

Поле `path` показывает, в каком месте пакета ошибка. Коды ошибок:

| Код | Что случилось | Что делать |
|---|---|---|
| `REQUIRED_FIELD_MISSING` | не заполнено обязательное поле | исправить на портале и прислать заново |
| `INVALID_FORMAT` | неверный формат, например ИНН не проходит проверку | исправить на портале |
| `REFERENCE_NOT_FOUND` | ссылка на то, чего нет в 1С, например на организацию договора | проверить номер и uid организации, шаг 7 |
| `DUPLICATE_CONFLICT` | несколько подходящих карточек в 1С | разобрать дубли, затем повторить обработку (§4.4) |
| `HEAD_CONTRAGENT_NOT_FOUND` | головной контрагент не найден за 3 попытки | сначала прислать головного, затем повторить обработку |
| `UNSUPPORTED_VERSION` | версия пакета не разрешена | проверить «Допустимые версии», шаг 5 |
| `INTERNAL_ERROR` | ошибка внутри 1С | смотреть журнал регистрации; 1С повторит сама до 3 раз |

### 6.8. Что 1С пропускает без ответа

| Пакет | Почему пропущен |
|---|---|
| `organization-id` = `5` или неизвестный код | пакет не для этой базы, в журнале этапов `filtered_out` |
| `sender` = `1c-rf` или `1c-kz` в топике `contragents` | свой пакет или пакет соседней базы |
| Статус в `contragents.exchange` не от `corp` | это статусы баз 1С, а не портала |
| Статус портала с неизвестным `correlation-id` | 1С такую карточку не отправляла |
| Статус `started`, пришедший после `completed` | старый или повторный статус |
| Пакет с тем же `id`, что уже обработан | повтор, второй раз не применяется |

## 7. Если что-то не работает

| Что видно | Вероятная причина | Что сделать |
|---|---|---|
| Группа в Kafka не STABLE, отставание растёт | консьюмеры не запущены | шаг 9: задание мониторинга включено? У карточек консьюмеров «Активен» и расписание? Для файловой базы: открыт ли сеанс 1С? |
| Карточки читаются, а статусы портала нет, или наоборот | файловая база: консьюмеры работают по очереди | см. [§8](#8-ограничения) |
| Ошибка подключения к Kafka | нет пароля или он неверный | шаг 3; проверка подключения в [Приложении Б](#приложение-б-вызовы-для-интегратора) |
| Карточка из 1С не уходит, «ожидает» без ошибки | не включён исходящий обмен или задание публикации | шаг 10 |
| Карточка из 1С в состоянии «ошибка», в тексте `contracts[0].organization` | у договора нет организации или у организации нет «Внешнего ID» | шаг 7, затем «Повторить отправку» |
| Ответ портала на карточку из 1С закончился `UNSUPPORTED_VERSION` | в «Допустимых версиях» нет `1.1.*` | шаг 5 |
| `DUPLICATE_CONFLICT` | дубли в справочнике контрагентов | §5; объединить или исправить дубли, затем повторить |
| Счёт или договор пропал из пакета портала, а в 1С остался с пометкой удаления | так и задумано: из пакета ушло, значит удалено на портале | ничего; если элемент вернётся в пакете, пометка снимется |
| В журнале регистрации предупреждение «Смещение в учёте … расходится со смещением группы …» | позиция чтения в 1С отстала от Kafka, например базу восстановили из копии | ничего; 1С продолжит читать с позиции Kafka |
| Пользователь не видит содержимое пакетов | нет роли диагностики | шаг 2 |

<a id="8-ограничения"></a>

## 8. Ограничения

- **Правки из 1С на портал не уходят.** Уходит только новая карточка. Существующие карточки массово не выгружаются.
- **Счета и договоры, добавленные позже 5 минут**, в отправленный пакет не попадают. Их нужно отправить кнопкой «Повторить отправку». Если портал пришлёт полное обновление без них, они получат пометку удаления.
- **Файловая база.** В одном сеансе фоновые задания выполняются по очереди. Консьюмер карточек работает непрерывно, поэтому консьюмер статусов может не запуститься совсем. Для рабочей эксплуатации нужна **клиент-серверная база**. На файловой базе консьюмеры придётся запускать в разных процессах; способ согласуйте с разработчиком.
- **Одна группа — одна база.** Группу `dev.1c.bp.rf` должна читать только эта база. Если её прочитает кто-то ещё, например копия базы, часть пакетов в эту базу не попадёт.
- **Документы** (счета, реализации, поступления) этим обменом не передаются, только контрагенты.

## Приложение Б. Вызовы для интегратора

Выполняются в консоли кода или во внешней обработке под пользователем с ролью диагностики.

```bsl
// Проверить пароль и подключение (пароль в ответ не попадает). Ожидается ok=1, ready=1
KFK_СекретыОкруженияСервер.ПроверитьГотовностьПодключенияKafka()

// Создать карточку консьюмера статусов портала по настройкам контура
KFK_ИсходящиеСнимкиСервер.ОбеспечитьКонсьюмерСтатусовПортала()

// Состояние, запуск и остановка консьюмеров
KFK_КонсьюмерЖизненныйЦиклСервер.Состояние("RF")      // active>=1 — работает
KFK_КонсьюмерЖизненныйЦиклСервер.ЗапуститьКонтур("RF")
KFK_КонсьюмерЖизненныйЦиклСервер.Остановить("RF")

// Повторно обработать пакет с портала, закончившийся ошибкой (тот же id пакета)
KFK_АдминистрированиеОбменаСервер.ПовторитьFailed("RF", "<id пакета>")

// Повторить отправку карточки из 1С (то же, что кнопка на Рабочем столе)
KFK_ИсходящиеСнимкиСервер.ПовторитьОтправку("RF", "<id пакета>")

// Очередь, возраст сообщений, число ошибок
KFK_АдминистрированиеОбменаСервер.СобратьМетрикиКонтура("RF")
```

Пересборка `.cfe` из исходников и контрольные суммы описаны в [`dist/README.md`](https://github.com/DmitrySkrypkin/1c-kafka-counterparties/blob/main/dist/README.md).
