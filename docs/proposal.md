# Proposal

## Why

Руководители проекта решили, что обмен контрагентами Портал ↔ 1С двусторонний и идёт по тем же топикам `contragents` / `contragents.exchange`. Сейчас контрагент, заведённый бухгалтером в 1С, на портал не попадает, и портал не может выдать ему свой `id`. Действующая спецификация `counterparty-exchange` описывает только входящий поток.

Выбран вариант A: 1С только **создаёт** контрагента, дальше им владеет портал. Последующие правки в 1С на портал не уходят.

## What Changes

- **Отправка снимка при создании.** Любая новая карточка `Справочник.Контрагенты` в базах РФ и КЗ, кроме созданных самим обменом и записанных с `ОбменДанными.Загрузка`, однократно публикуется в `contragents` как `contragent_created`. Отправитель — `1c-rf` / `1c-kz`, `organization-id` — код своего контура (`1` / `5`). В снимок входят карточка, контакты, адреса, банковские счета и договоры.
- **`uid` генерирует 1С.** При создании `uid` карточки равен GUID её ссылки и записывается в `KFK_ВнешнийUID` той же транзакцией. Так же получают `uid` банковские счета и договоры из снимка. Kafka key — `uid`.
- **Transactional Outbox для исходящих снимков.** Запись в очередь идёт в одной транзакции с созданием карточки. Публикация выполняется в фоне после настраиваемой задержки, чтобы в снимок попали счета и договоры, введённые сразу после карточки.
- **Приём ответа портала.** Новая consumer group каждого контура читает `contragents.exchange` и принимает только `sender=corp`. Статусы Started / Completed / Failed сопоставляются с исходящим сообщением по `correlation-id`. Failed портала виден администратору и повторяется только явной командой.
- **Привязка `id` портала.** Последующий `contragent_updated` от портала с `id`+`uid` находит карточку по `uid` и связывает `KFK_ВнешнийID`. Так же по `uid` связываются счета и договоры.
- **Контракт 1.1.0 (BREAKING для валидатора портала).** В теле от `sender ≠ corp` числовой `id` необязателен, а `uid` обязателен. Ключ банковского счёта — `id` **или** `uid`, как у договора. Сообщения портала (`sender=corp`) по-прежнему обязаны нести `id`. Допустимые версии контура — `1.0.*` и `1.1.*`.
- **Поиск по `uid` в 1С.** Входящий счёт ищется по `id`, затем по `uid`. Сценарий «`updated` без совпадений создаёт карточку» закрепляется явно: это штатный путь, по которому контрагент из одной базы попадает в другую после рассылки портала без `organization-id`.
- Национальные проверки ИНН / БИН / ИИН **не меняются**. В чужом контуре снимок, не прошедший проверку, получает терминальный Failed и не создаётся. Это принятый исход.

### Out of scope / Non-goals

- Отправка изменений карточки, созданной в 1С, после первой отправки. Последующие правки в 1С на портал не уходят.
- Отправка существующих контрагентов без `uid` (около 109 тыс. в РФ, около 2,9 тыс. в КЗ) и любая первоначальная выгрузка.
- Проверка регистрационного номера по `country` вместо правил контура-получателя.
- Отдельные исходящие топики (`from-1c.*`) и обмен другими сущностями.
- Изменение типовых конфигураций `src/cf` и `src/cf_bp_kz`: всё делается в расширении `ИнтеграцияApacheKafka`.
- Защита счетов и договоров, добавленных в 1С **после** отправки снимка, от пометки на удаление полным снимком портала. Это действующее поведение `counterparty-exchange`, и оно не меняется.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `counterparty-exchange`: появляется исходящий снимок при создании карточки в 1С, приём статусов портала и привязка `id` по `uid`. Меняются требования к телу (`id` при `sender ≠ corp`), к ключу банковского счёта (`uid`), к допустимому `sender`, к поиску счёта и к версиям контракта.

## Impact

- **Расширение РФ** `src/cfe/ИнтеграцияApacheKafka` и **расширение КЗ** `src/cfe_bp_kz/ИнтеграцияApacheKafka`: новая подписка на событие записи `Справочник.Контрагенты`, новый регистр исходящих снимков, сериализатор снимка, publisher, consumer статусов портала, новые ресурсы `KFK_НастройкиКонтуров`, команды администратора, поиск счёта по `uid`.
- **Контракт** `contract/counterparty/1.1.0`: JSON Schema, fixtures, каталог кодов. Каталог `1.0.0` остаётся без изменений.
- **Kafka**: новая consumer group каждого контура на `contragents.exchange`. ACL: 1С получает WRITE на `contragents`, READ на `contragents.exchange`; портал получает READ на `contragents` своей группой и WRITE на `contragents.exchange`.
- **Портал**: приём `contragent_created` от `1c-rf` / `1c-kz`, хранение `uid` карточки, счёта и договора, ответ статусами с `sender=corp`, затем `contragent_updated` с `id`+`uid`. Документ для команды портала — `задание-порталу-исходящие-контрагенты.md` в этом change.
- **Данные**: карточки 1С получают `KFK_ВнешнийUID` при создании. На существующие карточки change не влияет.

## Definition of Done

Критерии связаны с требованиями дельты [specs/counterparty-exchange/spec.md](specs/counterparty-exchange/spec.md). Среда проверки: dev-базы `БП_РФ` и `БП_КЗ`, тестовый кластер Kafka `local` (Kafbat UI), портал или его эмуляция публикацией в Kafka.

- [x] **OUT-1** Создание карточки пользователем в РФ и в КЗ даёт ровно одну запись Outbox и одно сообщение `contragent_created` в `contragents`: `sender` своего контура, `organization-id` своего контура, key = `uid`, тело проходит схему `1.1.0`. Карточка из входящего обмена и запись с `ОбменДанными.Загрузка` сообщения не дают. *Метод:* запрос к регистру через MCP базы + чтение топика через Kafbat API. *(passed: COM payload+sent; Kafbat browse blocked)*
- [x] **OUT-2** `uid` карточки равен GUID её ссылки и записан в `KFK_ВнешнийUID` до фиксации транзакции создания. Откат записи карточки не оставляет записи Outbox. *Метод:* запрос через MCP базы; тест отката.
- [x] **OUT-3** Счета и договоры, введённые в пределах задержки отправки, попадают в снимок со своими `uid`. Повторная запись карточки второго сообщения не создаёт. *Метод:* сценарий в dev-базе + чтение топика.
- [x] **OUT-4** Недоступность Kafka не теряет снимок: запись остаётся `pending` и уходит после восстановления с тем же message `id`. *Метод:* отключение брокера в настройке, повторный запуск publisher.
- [x] **OUT-5** Consumer статусов принимает только `sender=corp`, сопоставляет Started / Completed / Failed по `correlation-id` и сохраняет `messages[]` Failed. Статусы `1c-rf` / `1c-kz` и чужие `correlation-id` пропускаются без изменения данных. *Метод:* публикация тестовых статусов в `contragents.exchange`. *(passed: COM handler; live lag Kafbat blocked)*
- [x] **OUT-6** `contragent_updated` портала с `id`+`uid` для карточки, созданной в 1С, обновляет ту же карточку (без дубля), связывает `KFK_ВнешнийID` у карточки, счетов и договоров и не помечает на удаление счета, пришедшие с тем же `uid`. *Метод:* публикация `updated` в `contragents`, запрос через MCP.
- [x] **OUT-7** Тот же `updated` без `organization-id` во втором контуре создаёт карточку, если снимок проходит его национальную проверку, и даёт Failed `INVALID_FORMAT` по `reg_number`, если не проходит. *Метод:* два fixture: российское юрлицо и российский ИП.
- [x] **OUT-8** Входящие сообщения портала версии `1.0.*` обрабатываются как раньше. Тело `corp` без `id` отклоняется `REQUIRED_FIELD_MISSING`. Счёт без `id` и без `uid` отклоняется. *Метод:* существующие fixtures `1.0.0` + новые негативные fixtures `1.1.0`.
- [x] **OUT-9** Команда администратора повторяет только выбранную failed-отправку и создаёт новое сообщение с новыми message `id` и `correlation-id`. Остальные записи не меняются. *Метод:* сценарий в форме администрирования.
- [x] **Гейты**: `syntaxcheck` всех изменённых модулей без ошибок; `verify_xml` / проверка загрузки метаданных расширения (`CheckCanApply` / `UpdateDBCfg` DumpResult=0) для РФ и КЗ. `check_1c_code` / `review_1c_code` — сервер `1c-code-check-mcp` недоступен; без него эти гейты остаются `blocked/unverified`, а не `passed`.
- [x] **Финальное ревью** изменений на корректность, транзакционные границы и защиту от зацикливания, без нерешённых блокирующих замечаний.
