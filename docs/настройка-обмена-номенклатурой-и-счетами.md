# Настройка обмена номенклатурой и счетами с порталом (БП РФ и БП КЗ)

**Обновлено:** 21.11.2026
**Для кого:** администратор 1С, у которого уже работает обмен контрагентами по инструкции администратора РФ или КЗ (`archive/2026-11-14-counterparty-exchange-outbound-from-1c`).

Ниже — только то, что добавляется к обмену контрагентами. Расширение то же, `ИнтеграцияApacheKafka`. Паролей в документе нет.

---

## Как это работает

```text
                 ┌──────────────────────── Kafka ────────────────────────┐
  Портал  ──▶   │ products            товары               (во все базы)  │  ──▶  1С РФ и 1С КЗ
  Портал  ──▶   │ invoices            счета покупателю (по организации)   │  ──▶  1С РФ или 1С КЗ
  Портал  ◀──   │ products.exchange   ответы по товарам                   │  ◀──  1С
  Портал  ◀──   │ invoices.exchange   ответы по счетам                    │  ◀──  1С
                 └────────────────────────────────────────────────────────┘
```

**Товары**
- Портал присылает товар в обе базы сразу, без номера организации. Каждая база ищет товар по `uid` портала. Если не находит, создаёт новый с тем же GUID.
- Новый товар, заведённый в 1С, уходит на портал через 5 минут. Правки существующих товаров из 1С не отправляются.

**Счета**
- Портал присылает счёт с номером организации. Счёт принимает база этой организации и создаёт или обновляет счёт на оплату покупателю.
- Если контрагент или товар счёта ещё не пришли, база ждёт их до 30 минут. Не дождалась — ошибка `REFERENCE_NOT_FOUND`.
- Новый счёт, заведённый в 1С, уходит на портал после того, как портал подтвердил его контрагента и новые товары. Правки счёта после первой записи из 1С не отправляются.

**Проведение**
- Счёт РФ проводится при создании и при каждом обновлении, в том числе после снятия пометки удаления.
- Счёт КЗ записывается без проведения.
- Если дата счёта попадает в закрытый период, изменение отклоняется с ошибкой `PERIOD_CLOSED`. В КЗ это действует и для полноправного пользователя заданий обмена: опция «Применять дату запрета для полных прав» для этого не нужна.

## Что подготовить заранее

| Что | У кого |
|---|---|
| Топики `products`, `products.exchange`, `invoices`, `invoices.exchange` | администратор Kafka |
| Права на чтение и запись в четыре новых топика для тех же групп, что у контрагентов (`dev.1c.bp.rf`, `dev.1c.bp.rf.exchange`; для КЗ — `…kz…`) | администратор Kafka |
| Подтверждение порталом, что он готов принимать товары и счета из 1С | команда портала |
| Ставки НДС портала и ставка 1С для каждой из них | бухгалтерия |
| Папка, вид номенклатуры, единица и ставка НДС для новых товаров с портала | бухгалтерия |

## Шаг 1. Обновите расширение

Обновите расширение в Конфигураторе, как в шаге 1 основной инструкции, затем **Обновить конфигурацию базы данных** (F7).

✔ **Проверка:** в **Kafka → Работа с данными** появились **(Kafka) Настройки объектов обмена** и **(Kafka) Ставки НДС портала**.

## Шаг 2. Проверьте настройки видов объектов

**Kafka → Работа с данными → (Kafka) Настройки объектов обмена.** На каждый контур три строки, по одной на вид: **Контрагент**, **Номенклатура**, **Счет на оплату покупателю**. Строки появляются сами при первом обращении, вручную их не создавайте.

| Поле | Контрагент | Номенклатура | Счет на оплату покупателю |
|---|---|---|---|
| Топик основной | `contragents` | `products` | `invoices` |
| Топик ответа | `contragents.exchange` | `products.exchange` | `invoices.exchange` |
| Входящий обмен включен | да | **нет** до шага 7 | **нет** до шага 7 |
| Исходящий обмен включен | как было | **нет** до шага 8 | **нет** до шага 8 |
| Задержка отправки секунд | как было | `300` | `300` |
| Версия исходящего контракта | `1.1.0` | `1.0.0` | `1.0.0` |
| Допустимые версии | `1.0.*;1.1.*` | `1.0.*` | `1.0.*` |
| Окно ожидания ссылок минут | — | — | `30` — сколько счёт ждёт контрагента, договор и товары |

Строка «Контрагент» повторяет прежние настройки контура. Сообщения выключенного вида консьюмер пропускает без ответа порталу. Включение и выключение вида действуют без перезапуска консьюмера, не позже чем через минуту.

## Шаг 3. Заполните умолчания для новых товаров

**(Kafka) Настройки контуров**, запись своего контура:

| Поле | РФ (dev) | КЗ (dev) |
|---|---|---|
| Группа номенклатуры портала | папка товаров портала | папка товаров портала |
| Вид номенклатуры по умолчанию | «Товар» | «Товары приобретенные» |
| Единица измерения по умолчанию | «шт» | «шт» |
| Ставка НДС номенклатуры по умолчанию | «Общая» | 16% (решение заказчика 19.11.2026) |

Умолчания действуют только при создании товара. У существующего товара обмен не меняет папку, вид, единицу и ставку. Если портал прислал `unit.okei`, единица берётся по коду ОКЕИ. Если нужное умолчание не заполнено, обмен отвечает ошибкой и товар не создаётся.

В той же записи заполните **«Склад по умолчанию»**. Он нужен для счетов, в которых портал не передал `uid` склада: так приходят счета КЗ. Если `uid` склада есть, счёт берёт склад по нему, а не умолчание. Если нет ни `uid`, ни умолчания, счёт отклоняется с ошибкой `REQUIRED_FIELD_MISSING` по `storehouse.uid`.

| Поле | РФ (dev) | КЗ (dev) |
|---|---|---|
| Склад по умолчанию | можно не заполнять: портал передаёт `uid` | «АНКАС склад KZ» |

## Шаг 4. Заполните таблицу ставок НДС

**Kafka → Работа с данными → (Kafka) Ставки НДС портала.** Одна строка на каждый процент, который может прийти в строке счёта:

| Код контура | Процент НДС | Ставка НДС (dev) |
|---|---|---|
| РФ | 22 / 10 / 0 | НДС 22% / НДС 10% / НДС 0% |
| КЗ | 16 / 12 / 10 / 5 / 0 | элементы справочника «Ставки НДС» с этими процентами |

- **Без НДС.** Строка счёта с `vat_percent` = null идёт без НДС, отдельная строка таблицы для этого не нужна. В РФ ставится «Без НДС». В КЗ — первая ставка справочника с признаком «Для освобождённого оборота».
- **Процента нет в таблице.** Счёт отклоняется с ошибкой `REFERENCE_NOT_FOUND` по `products[i].vat_percent`.
- **Исходящий счёт.** Процент для портала ищется по той же таблице в обратную сторону. Если ставки строки нет в таблице, счёт не уходит, в его записи будет та же ошибка.

## Шаг 5. Только КЗ: свяжите старые товары с порталом

GUID товаров КЗ не совпадают с `uid` портала. Поэтому `uid` один раз записывается в реквизит товара «Внешний UID»: пары «товар КЗ — `uid`» собираются из квитанций старого обмена. В dev это сделано для 3 511 товаров. Ещё 1 071 товар связан по однозначному совпадению наименования или артикула с товаром портала в базе РФ (`kz-name-matched.csv`). Перед рабочей базой этот список должна просмотреть бухгалтерия КЗ. Не связаны 121 товар: неоднозначные совпадения и товары без пары.

Для рабочей базы связывание выполняет интегратор. Вызов в консоли кода:
- `KFK_АдаптерНоменклатурыСервер.ПривязатьUIDПортала(Пары, Истина)` — пробный прогон, ничего не записывает;
- затем тот же вызов с `Ложь` — записывает.

Без связывания портал создаст в КЗ дубли этих товаров.

**Только РФ: контрагенты.** Старые карточки РФ портал получил из 1С, поэтому `uid` портала равен GUID карточки, а реквизит «Внешний UID» у них пуст (в dev заполнен у 24 карточек из 109 316). Счёт портала находит такую карточку и по GUID. Решение заказчика: перед запуском в рабочей базе РФ интегратор один раз заполняет «Внешний UID» всех карточек их GUID, тогда карточки по ключам портала находит и обмен контрагентами. Вызов в консоли кода (только база РФ):
- `KFK_ИдентичностьКонтрагентаСервер.ЗаполнитьВнешнийUIDПоGUID(Истина)` — пробный прогон, ничего не записывает, показывает, сколько карточек будет заполнено и сколько конфликтов;
- `KFK_ИдентичностьКонтрагентаСервер.ЗаполнитьВнешнийUIDПоGUID(Ложь, 10000)` — записывает порцию из 10 000 карточек. Повторяйте, пока в ответе `left=0`.

Заполняются только карточки с пустым «Внешний UID», не группы и без пометки удаления. Уже заполненные не меняются. Карточка, чей GUID уже записан у другой карточки, пропускается (`conflict`, до 50 GUID в ответе). Запись идёт без бизнес-проверок и без регистрации в планах обмена: изменение не уходит в синхронизацию с другими базами. Занятая пользователем карточка попадает в `errors` и в журнал регистрации (событие `Kafka.Identity.FillUID`) и заполнится при следующем вызове. Удобнее запускать вне рабочего времени.

## Шаг 6. Добавьте топики консьюмерам и включите задание повтора

1. **Kafka → Справочники → Консьюмеры.** Один консьюмер контура читает все три основных топика, второй — все три топика ответов:
   - карточка с идентификатором группы `dev.1c.bp.rf` (`…kz`): вкладка **Топики** — `contragents`, `products`, `invoices`;
   - карточка `dev.1c.bp.rf.exchange` (`…kz.exchange`): `contragents.exchange`, `products.exchange`, `invoices.exchange`.

   Остальные параметры не меняйте. Для новых топиков группа начнёт читать с позиции, заданной `auto.offset.reset`.
2. **Регламентные и фоновые задания** → **Задание повтора входящих**: пользователь из шага 2 основной инструкции, флажок **«Использование»**, расписание раз в минуту. Задание повторно обрабатывает сообщения, которые ждут ответа: счёт ждёт товар, следующее сообщение того же ключа ждёт предыдущее.

   При первом запуске в dev РФ задание доведёт 3 старых тестовых процесса и отправит по ним статусы (вопрос Q3).

**Тип базы.**
- **Клиент-серверная база** — штатный вариант. Консьюмеры и задание повтора работают фоновыми заданиями на сервере 1С параллельно.
- **Файловая база.** Платформа выполняет одновременно только одно фоновое задание, остальные ждут в очереди. Первый консьюмер слушает без остановки, поэтому второй консьюмер и задание повтора не стартуют. Кроме того, фоновые задания файловой базы выполняются, только пока открыт сеанс 1С. Если база файловая, на компьютере с базой запустите отдельным внешним соединением каждый консьюмер (`KFK_Интеграция.СлушатьСообщения` с данными карточки) и задание повтора (по расписанию планировщика Windows, раз в минуту). Так работал живой прогон 19.11.2026. Тип рабочих баз уточняется (вопрос Q12).

## Шаг 7. Включите приём

1. Строка **Номенклатура**: **«Входящий обмен включен»** = ✔.
2. Проверка: попросите портал изменить тестовый товар. Через минуту:
   - в **(Kafka) Журнал этапов** есть `started` и `completed`;
   - у товара в 1С «Внешний UID» = `uid` портала;
   - дубля нет.
3. Строка **Счет на оплату покупателю**: **«Входящий обмен включен»** = ✔.
4. Проверка: попросите портал прислать тестовый счёт для вашей организации. Счёт есть в журнале «Счета на оплату покупателю», реквизит «Номер портала» заполнен, в ответе `completed` портал получил номер 1С.

## Шаг 8. Включите отправку из 1С

Включайте после подтверждения портала. Сначала товары, затем счета:

1. Строка **Номенклатура**: **«Исходящий обмен включен»** = ✔.
2. Строка **Счет на оплату покупателю**: **«Исходящий обмен включен»** = ✔.
3. **Задание публикации исходящих снимков** уже включено для контрагентов. Если нет — включите его.

✔ **Проверка.** Заведите товар, затем счёт с этим товаром. В **(Kafka) Рабочий стол**, вкладка **Исходящие снимки**:
1. Товар уходит через 5 минут: «Отправлен», затем «Завершён».
2. Счёт ждёт ответа портала по товару. В диагностике записи — `waiting:products[0].uid`.
3. После ответа портала счёт уходит при следующем запуске задания.

Если портал отклонил контрагента или товар счёта, запись счёта переходит в «Ошибка» с `DEPENDENCY_FAILED`. Исправьте объект, затем повторите отправку счёта кнопкой на рабочем столе.

Если у организации счёта не заполнен «Внешний ID» (шаг 7 основной инструкции), счёт не уходит. Его запись получает ошибку `organization`.

## Шаг 9. Новые имена типов сообщений

**(Kafka) Настройки контуров**, поле **«Новые имена типов»**:

| Значение | Что отправляет 1С |
|---|---|
| нет (по умолчанию) | прежние имена: `contragent_created`, `product_created`, `invoice_exchange_completed` |
| да | новые имена: `contragent.created`, `product.created`, `invoice.exchange_completed` |

Принимает 1С оба написания при любом значении. Переключайте, когда портал подтвердит, что принимает новые имена. Переключение одно на весь контур.

## Откат

| Что случилось | Что сделать |
|---|---|
| Ошибки в приёме товаров или счетов | снимите «Входящий обмен включен» у вида. Новые сообщения пропускаются, контрагенты работают как раньше |
| Ошибки в отправке из 1С | снимите «Исходящий обмен включен» у вида. Записи в «Исходящих снимках» остаются в очереди и уйдут после повторного включения |
| Портал не понимает новые имена типов | снимите «Новые имена типов» |
| Нужно вернуть прежнюю версию расширения | загрузите предыдущий `.cfe` и обновите конфигурацию базы. Новые реквизиты и регистры удалятся вместе с данными: «Внешний UID» товаров КЗ, номера портала у счетов, таблица ставок. Сохраните выгрузку до отката |

## Приложение. Для интегратора

**Вызовы в консоли кода:**

```bsl
KFK_НастройкиКонтуровСервер.ПрочитатьНастройкиВида("RF", Перечисления.KFK_ВидыОбъектовОбмена.СчетНаОплатуПокупателю)
KFK_АдаптерНоменклатурыСервер.СобратьИсходящийСнимок(Товар)          // тело product.created
KFK_АдаптерСчетовСервер.СобратьИсходящийСнимок(Счет, "RF")            // тело invoice.created
KFK_АдаптерСчетовСервер.ЗависимостиИсходящегоСчета(Счет)              // кого ждёт исходящий счёт
KFK_АдаптерНоменклатурыСервер.ПривязатьUIDПортала(Пары, Истина)       // КЗ: пробное связывание
KFK_ИдентичностьКонтрагентаСервер.ЗаполнитьВнешнийUIDПоGUID(Истина)       // РФ: пробное заполнение внешнего UID
KFK_ИдентичностьКонтрагентаСервер.ЗаполнитьВнешнийUIDПоGUID(Ложь, 10000)  // РФ: порция 10 000, повторять до left=0
```

**Контракты** лежат в каталоге расширения: `contract/product/1.0.0`, `contract/invoice/1.0.0`. Там схемы, примеры и `validate_fixtures.py`.
