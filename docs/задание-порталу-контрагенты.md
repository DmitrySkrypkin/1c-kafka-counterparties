# Задание для команды портала и Kafka: обмен контрагентами

**Аудитория:** команда портала Корп и администраторы Kafka  
**Дата:** 1 ноября 2026  
**Контракт:** OpenSpec `counterparty-exchange-from-tz`, schema `1.0.0`  
**Машиночитаемые схемы:** `src/cfe/ИнтеграцияApacheKafka/contract/counterparty/1.0.0/`

Этот документ — только контрагенты. Документы, номенклатура и `from-1c.*` сюда не входят.

Пароли и ключи в документ не входят.

## 1. Топики

| Топик | Направление | Пишет | Читает | Содержимое |
| --- | --- | --- | --- | --- |
| `contragents` | Портал → 1С | портал (`corp`) | consumer group РФ и отдельно КЗ | `contragent_created`, `contragent_updated` |
| `contragents.exchange` | 1С → Портал | `1c-rf` и `1c-kz` | consumer group портала | `contragent_exchange_started` / `_completed` / `_failed` |

Требования к Kafka:

- Топики создаются **заранее**; на prod — `auto.create.topics.enable=false`.
- Для текущего профиля — 1 partition на `contragents` (при росте числа partition key остаётся обязательным).
- Cleanup: `delete`. Compaction не использовать для этого потока.
- Retention бизнес/статусных топиков — по стандарту кластера; зафиксировать фактические значения в ответе команде 1С.

## 2. Consumer groups 1С

| Окружение | РФ | КЗ |
| --- | --- | --- |
| dev | `dev.1c.bp.rf` | `dev.1c.bp.kz` |
| test | `test.1c.bp.rf` | `test.1c.bp.kz` |
| prod | `prod.1c.bp.rf` | `prod.1c.bp.kz` |

У каждой базы своя группа на один и тот же топик `contragents`. Иначе Kafka раздаст сообщения между контурами.

Имя группы портала для `contragents.exchange` выбирает портал и сообщает для ACL.

## 3. ACL (минимум)

Principal 1С РФ / КЗ:

- READ, DESCRIBE: `contragents`
- WRITE, DESCRIBE: `contragents.exchange`
- READ на свою consumer group
- DESCRIBE кластера (проверка брокера при старте)

Principal портала:

- WRITE: `contragents`
- READ: `contragents.exchange`
- READ на свою группу статусов

Учётные данные передаются вне репозитория.

## 4. Kafka key

| Условие | Key |
| --- | --- |
| В теле есть `uid` | строка UUID `uid` |
| `uid` нет | строковое представление числового `id` контрагента |

Все события одного ключа должны оставаться в одном partition. Нельзя параллельно слать обновления одного контрагента то по `id`, то по `uid` как по разным ключам.

## 5. Заголовки входящего сообщения

Обязательные:

| Заголовок | Правило |
| --- | --- |
| `sender` | непустая строка (портал) |
| `correlation-id` | UUID операции; вернётся во всех статусах |
| `id` | UUID **сообщения** (идемпотентность). Повтор той же доставки — тот же `id` |
| `type` | `contragent_created` или `contragent_updated` |
| `version` | major 1, например `1.0.0` (allow-list контура `1.0.*`) |
| `timestamp-ms` | Unix time в **миллисекундах**, ровно 13 цифр |

Необязательный:

| Заголовок | Правило |
| --- | --- |
| `organization-id` | `1` → только РФ; `5` → только КЗ; **отсутствие** → оба контура; иное значение чужой контур тихо пропускает **без** статуса |

Важно:

- `id` в заголовке — не числовой `id` контрагента из тела.
- Десятизначный timestamp (секунды) — ошибка формата (`INVALID_FORMAT`).

## 6. Тело снимка

Каждое сообщение — **полный** актуальный снимок. Отдельного поля `snapshot` нет. И `created`, и `updated` несут полный набор.

Минимум: числовой `id`, непустое `name`.

Опционально (nullable): `uid`, `kpp`, `ogrn`, `name_short`, флаги отношений, `is_separate`, `type_entity`, `reg_number`, `head_contragent`, `additional_information`, `country`, коллекции `emails`, `phones`, `addresses`, `bank_accounts`, `contracts`.

Правила коллекций:

- Отсутствующая / null / пустая коллекция = пустой набор.
- Банковский счёт обязан иметь стабильный `id`.
- Договор — хотя бы один ключ: `id` или `uid`.
- Тип договора: `realization` или `purchase`.
- Тип адреса: `actual`, `legal`, `postal`.
- `type_entity`: `legal`, `physical_person`, `legal_outside`, `sole_proprietor`.

Организация договора:

- обязательны `organization.id` и `organization.uid`;
- `organization.uid` — GUID существующей организации в целевой базе 1С;
- код организации в 1С должен совпасть с `organization.id`.

Полные схемы и fixtures: каталог `contract/counterparty/1.0.0` (в т.ч. пример ТЗ «АО СОГАЗ»).

## 7. Статусы в `contragents.exchange`

Последовательность на каждом контуре:

1. Ровно один логический `contragent_exchange_started` (до валидации тела и записи в 1С).
2. Ровно один конечный: `contragent_exchange_completed` или `contragent_exchange_failed`.

Общие поля статуса:

- новый UUID сообщения статуса;
- тот же `correlation-id`, что у входа;
- `sender`: `1c-rf` или `1c-kz`;
- `timestamp-ms`, `type`, `version`;
- в теле — `id` контрагента и `uid`, если был.

Failed дополнительно содержит непустой массив `messages[]`:

| Поле | Смысл |
| --- | --- |
| `code` | код из каталога |
| `path` | JSON path поля или `null` |
| `message` | человекочитаемый текст |

Каталог кодов (только эти):

- `REQUIRED_FIELD_MISSING`
- `INVALID_FORMAT`
- `UNSUPPORTED_VERSION`
- `REFERENCE_NOT_FOUND`
- `HEAD_CONTRAGENT_NOT_FOUND`
- `DUPLICATE_CONFLICT`
- `INTERNAL_ERROR`

Валидатор собирает **все** независимые ошибки в один Failed.

Портал обязан:

- принимать независимые ответы РФ и КЗ по одному `correlation-id`;
- быть идемпотентным к техническим повторам статуса (один логический результат на контур).

## 8. Поведение 1С, которое должен знать портал

| Ситуация | Поведение |
| --- | --- |
| Повтор того же message `id` | Бизнес повторно не применяется |
| Тот же `id`, другой payload | Новая доставка в карантин; исходный результат не меняется |
| Нет головы `head_contragent` | До 3 попыток, затем `HEAD_CONTRAGENT_NOT_FOUND` |
| Ошибка схемы / дубликат | Сразу Failed, без отложенного retry |
| Счёт/договор исчез из снимка | Удаляется в 1С (включая ручные) |
| Нельзя удалить ребёнка | Откат снимка, `INTERNAL_ERROR` |

Числовой SLA на latency нет. Первый проход без искусственной задержки; задержки только на retry.

## 9. Что передать команде 1С

- Bootstrap-адреса test/prod.
- Протокол безопасности и способ передачи пароля (env / файл / хранилище) — без публикации секрета в git.
- Подтверждение топиков и ACL (`kafka-topics --describe`, `kafka-acls --list`).
- Имя consumer group портала для `contragents.exchange`.
- Фактический retention и число partition.

## 10. Чек-лист готовности портала

1. Публикация `contragent_created` / `_updated` с корректными headers и key.
2. `timestamp-ms` всегда 13 цифр.
3. `organization-id` выставляется осознанно (1 / 5 / отсутствует).
4. Снимок полный; исчезнувшие счета и договоры сознательно убраны из JSON.
5. Чтение `contragents.exchange`: Started, затем Completed или Failed; разбор `messages[]`.
6. Обработка двух независимых контуров на broadcast.
7. Повторная публикация с тем же message `id` не ломает карточку на стороне портала.
