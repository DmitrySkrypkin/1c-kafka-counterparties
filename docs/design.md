# Design

## Context

Зачем это нужно, описано в [proposal.md](proposal.md); проверяемое поведение — в [specs/counterparty-exchange/spec.md](specs/counterparty-exchange/spec.md). Действующее поведение входящего потока — [openspec/specs/counterparty-exchange/spec.md](../../specs/counterparty-exchange/spec.md).

Состояние расширений РФ (`src/cfe/ИнтеграцияApacheKafka`) и КЗ (`src/cfe_bp_kz/ИнтеграцияApacheKafka`), важное для решения:

- У `Контрагенты`, `БанковскиеСчета` и `ДоговорыКонтрагентов` уже есть `KFK_ВнешнийID` (Число 19) и `KFK_ВнешнийUID` (Строка 36, индексирован). Справочник `Контрагенты` иерархический: в нём есть группы.
- Consumer `contragents` обрабатывает только `sender = "corp"` (`KFK_Интеграция:476`). Сообщения `1c-rf` / `1c-kz` в этом же топике он уже пропускает. Защита от эха на приёме есть, её нужно только закрепить в спецификации и журналировать.
- Входящий адаптер пишет карточку и детей с `ОбменДанными.Загрузка = Истина`.
- Подписок на события в расширениях нет. Регламентные задания: `KFK_ЗаданиеМониторингаКонсьюмеров`, `KFK_ЗаданиеОчисткиХранения`.
- Статусы публикуются из Outbox `KFK_ИсходящиеСтатусы` функцией `KFK_ИсходящиеСтатусыСервер.ОпубликоватьОжидающие` → `KFK_Интеграция.Опубликовать` (синхронно, ключ и заголовки передаются строкой).
- Настройки контура — `KFK_НастройкиКонтуров` (`Отправитель`, `ТопикВходящий`, `ТопикСтатусов`, `ГруппаПотребителя`, `ДопустимыеВерсии`, сроки хранения и пороги).
- Банковский счёт во входящем потоке ищется только по `KFK_ВнешнийID` (`НайтиБанковскийСчетПоВнешнемуID`), договор — по `id` и `uid` (`НайтиДоговорПоВнешнимКлючам`). Для аудита уже есть сериализаторы детей `СериализоватьБанковскиеСчета*` / `СериализоватьДоговоры*`.
- Контракт `contract/counterparty/1.0.0`: в теле `id` обязателен, у `bankAccount` обязателен `id`, `uid` нет.

## Goals / Non-Goals

**Goals:**

- снимок созданной в 1С карточки уходит не больше одного раза и не теряется при сбое Kafka;
- отправка не может вызвать цикл: запись, сделанная обменом, никогда не порождает исходящее сообщение;
- ответ портала связывает `id` с той же карточкой, счетами и договорами без дублей;
- входящий поток версии `1.0.*` работает без изменений, пока портал не перейдёт на `1.1`;
- исходящий обмен включается отдельной настройкой контура и по умолчанию выключен.

**Non-Goals:**

- исходящая отправка из групп справочника `Контрагенты`;
- синхронная отправка из транзакции записи карточки;
- автоматический повтор отправки после Failed портала.

## Decisions

### 1. Своя подписка на события в расширении

В каждом расширении появляется подписка `KFK_РегистрацияИсходящегоКонтрагента` на `Справочник.Контрагенты` (`СправочникОбъект.Контрагенты`) с двумя обработчиками в новом модуле `KFK_ИсходящиеСнимкиСервер`:

- **`ПередЗаписью`**: работает только при `ЭтоНовый()`, `Не ЭтоГруппа`, `Не ОбменДанными.Загрузка`, без признака `ДополнительныеСвойства.KFK_ЗаписьОбменом` и при включённом исходящем обмене контура. Если `ПолучитьСсылкуНового()` пуста, ставит `УстановитьСсылкуНового(Справочники.Контрагенты.ПолучитьСсылку(Новый УникальныйИдентификатор))`. Пустой `KFK_ВнешнийUID` заполняет строкой GUID этой ссылки и помечает объект в `ДополнительныеСвойства.KFK_РегистрироватьИсходящий`.
- **`ПриЗаписи`**: по этой пометке создаёт запись исходящей очереди в той же транзакции.

Входящий адаптер дополнительно ставит `ДополнительныеСвойства.KFK_ЗаписьОбменом = Истина`. Сейчас он и так пишет с `ОбменДанными.Загрузка`, но это поведение он может в будущем поменять, а явная пометка от этого не зависит.

Отвергнутая альтернатива — `&После("ПриЗаписи")` в модуле заимствованного объекта. Она меняет модуль объекта типовой конфигурации на поддержке. Подписка же живёт целиком в расширении и не трогает модуль объекта.

### 2. Отдельный регистр исходящих снимков

Новый регистр сведений `KFK_ИсходящиеСнимки` (независимый, непериодический):

- измерения: `КодКонтура`, `ИдентификаторСообщения`;
- ресурсы: `Контрагент` (`СправочникСсылка.Контрагенты`), `ИдентификаторКорреляции`, `Состояние` (новое перечисление `KFK_СостоянияИсходящегоСнимка`: `pending`, `sent`, `started`, `completed`, `failed`), `НеРаньше`, `НомерПопытки`, `Payload`, `СообщенияПортала`, `Диагностика`, `ИсходнаяЗапись` (message id исходной записи при повторной отправке), `ДатаЗаписи`.

`KFK_ИсходящиеСтатусы` не используется: у статуса другой жизненный цикл (последовательности 10/20, привязка к входящему процессу), и смешение двух очередей усложнит publisher и очистку. Одна карточка получает запись только при создании. Повторная отправка администратором — это новая запись со ссылкой на исходную.

### 3. Отложенная публикация, тело собирается в момент отправки

Новое регламентное задание `KFK_ЗаданиеПубликацииИсходящихСнимков` (период 60 секунд) выбирает записи `pending` с `НеРаньше ≤ ТекущаяДатаСеанса()` пачкой `РазмерПачки`. `НеРаньше` = время создания + `ЗадержкаОтправкиСекунд`.

**Значение по умолчанию — 300 секунд.** Банковские счета и договоры подчинены карточке, их можно ввести только после её записи. Без задержки они почти никогда не попали бы в снимок. Пяти минут хватает на ввод реквизитов при создании, и для портала это небольшая задержка. Значение настраивается.

Перед публикацией в одной транзакции:

1. дети карточки без `KFK_ВнешнийUID` получают его равным GUID своей ссылки (запись с `ОбменДанными.Загрузка` и `KFK_ЗаписьОбменом`, поэтому подписка их не видит);
2. собирается тело `1.1.0`, оно сохраняется в `Payload`.

Затем вызывается `KFK_Интеграция.Опубликовать`: топик — `ТопикВходящий` контура (`contragents`), ключ — `uid` карточки, заголовки — по требованию *Outbound message contract*. Успех → `sent`. Ошибка → запись остаётся `pending`, `НомерПопытки + 1`, `НеРаньше` сдвигается по `БазоваяЗадержкаСекунд` × 2^(попытка − 1), но не дальше `МаксимальнаяЗадержкаСекунд`. Message `id` не меняется. Отдельного лимита попыток нет: снимок не теряется, а возраст старейшей `pending` попадает в мониторинг по существующему `ПорогВозрастаМинут`.

### 4. Сериализатор — обратное отображение адаптера контура

В модулях `KFK_АдаптерКонтрагентовРФСервер` и `KFK_АдаптерКонтрагентовКЗСервер` появляется `СобратьИсходящийСнимок(Контрагент)`. Он использует то же соответствие полей, что и запись входящего снимка в этом контуре: ИНН/КПП/ОГРН в РФ, `ИдентификационныйКодЛичности` в КЗ, отношения `KFK_Поставщик` и т.д., контактная информация, страна. Сериализаторы детей для аудита берутся за основу. Ключи детей — `id` (если есть `KFK_ВнешнийID`) и `uid`.

- Организация договора: `{id: внешний код организации, uid: GUID ссылки}`. Это обратная функция к `РазрешитьОрганизациюДоговора*`.
- `head_contragent` передаётся, только если у головного контрагента есть `KFK_ВнешнийID` или `KFK_ВнешнийUID`. Иначе поле не передаётся, а в журнал пишется предупреждение. Голова, неизвестная порталу, дала бы у портала `HEAD_CONTRAGENT_NOT_FOUND` и Failed на весь снимок.
- Перед публикацией тело проверяется тем же контурным валидатором в режиме «отправитель 1С». Невалидный снимок становится `failed` с локальной диагностикой и в Kafka не уходит.

### 5. Контракт 1.1.0 и валидатор

Каталог `contract/counterparty/1.1.0` лежит рядом с `1.0.0` (README, `headers.schema.json`, `body.schema.json`, fixtures). Отличия от `1.0.0` перечислены в требовании *Contract version coexistence*. Обязательность `id` / `uid` в схеме задаётся через `if/then` по `sender`. В `body.schema.json` нет заголовков, поэтому для `1.1.0` проверку по отправителю делает кодовый валидатор, а схема требует `anyOf: [id, uid]`.

`KFK_СнимокКонтрагентаСервер.ПроверитьБазовыеПоля` получает параметр «отправитель». Для `corp` числовой `id` обязателен в любой версии. `ПроверитьБанковскиеСчета` принимает `id` или `uid`. `ДопустимыеВерсии` контура по умолчанию — `1.0.*;1.1.*`.

### 6. Поиск счёта по `id`, затем по `uid`

`НайтиБанковскийСчетПоВнешнемуID` заменяется функцией поиска по обоим ключам в пределах владельца, по образцу `НайтиДоговорПоВнешнимКлючам`. Правила: нашли один счёт — обновить и дописать недостающий ключ; ключи указывают на разные счета — `DUPLICATE_CONFLICT`. Мягкое удаление отсутствующих счетов сравнивает снимок с найденными счетами, а не со списком `id`. Иначе счёт, найденный по `uid`, был бы помечен на удаление.

### 7. Consumer статусов портала

В каждом контуре заводится отдельный consumer в `KFK_Консьюмеры` на `ТопикСтатусов` (`contragents.exchange`) с новой группой `ГруппаПотребителяСтатусовПортала`: `<env>.1c.bp.rf.exchange` / `<env>.1c.bp.kz.exchange`. Группа своя, чтобы смещения статусов не смешивались с группой `contragents` и чтобы её можно было останавливать отдельно.

Обработчик `KFK_ИсходящиеСнимкиСервер.ОбработатьСтатусПортала`:

- принимает только `sender = corp` и `correlation-id`, известный этому контуру;
- переводит запись по монотонной цепочке `sent → started → completed | failed`. Повтор или более старый статус ничего не меняют, поэтому повторная доставка Kafka безопасна;
- у failed сохраняет `messages[]` в `СообщенияПортала`;
- пишет этап в `KFK_ЖурналЭтапов`;
- фиксирует offset после записи. Отдельный Inbox для статусов не нужен: обработка идемпотентна и не меняет бизнес-данные.

Цикл `СлушатьСообщения` передаёт обработчику **каждое** сообщение из `ТопикСтатусов`, не только `corp`. Обработчик сам пропускает чужого отправителя и сообщения без `id` / `correlation-id`. До 11.11.2026 не-`corp` статусы журналировались прямо в цикле, и сообщение без заголовков (в dev-топике оно лежит на смещении 32) вызывало исключение «Не заполнен идентификатор сообщения»: задание падало без фиксации offset и останавливалось на этом сообщении при каждом перезапуске.

Связь `id` портала с карточкой приходит не со статусом, а с последующим `contragent_updated` через обычный входящий поток (решения 6 и требование *Deterministic counterparty lookup*). Поэтому `completed` от портала не меняет карточку.

### 8. Повторная отправка — новое сообщение

Команда «Повторить отправку» в обработке `KFK_РабочийСтол` (список исходящих снимков с фильтром по состоянию) доступна для `failed` и для `pending` с ошибкой транспорта. Она создаёт новую запись: новые message `id` и `correlation-id`, `ИсходнаяЗапись` = исходная, тело собирается заново. Повторять тот же message `id` нельзя: портал уже обработал его как Failed и по правилам идемпотентности не начнёт второй жизненный цикл.

### 9. Настройки и права

Новые ресурсы `KFK_НастройкиКонтуров`: `ИсходящийОбменВключен` (Булево, по умолчанию Ложь), `ЗадержкаОтправкиСекунд` (300), `ГруппаПотребителяСтатусовПортала`, `ВерсияИсходящегоКонтракта` (`1.1.0`). Сроки хранения `Payload` и `СообщенияПортала` — существующий `СрокХраненияИсходящихДней`. Компактная запись (ключи и состояние) не удаляется, чтобы администратор видел историю отправок. Очистку выполняет `KFK_ЗаданиеОчисткиХранения`.

Роли `KFK_СервисОбмена` и `KFK_ДиагностикаОбмена` получают права на новый регистр, перечисление и задание. Обычному пользователю, который создаёт контрагента, отдельные права не нужны: регистрация идёт из подписки в привилегированном режиме, только запись `KFK_ИсходящиеСнимки` и только в обработчике.

### 9a. Порядок поиска карточки: внешние ключи раньше регистрационных данных

Решение пользователя от 11.11.2026 (вариант A после живого прогона). `KFK_ИдентичностьКонтрагентаСервер.РазрешитьКонтрагента` ищет по `id` и `uid`. Если они нашли одну карточку, она обновляется, а ИНН+КПП (в КЗ — БИН/ИИН) не проверяются. Регистрационные данные используются только когда ни `id`, ни `uid` ничего не нашли; несколько совпадений тогда дают `DUPLICATE_CONFLICT`. Конфликт по-прежнему возникает, если `id` и `uid` указывают на разные карточки.

Причина: прежний код проверял ИНН+КПП всегда и отказывал при нескольких совпадениях даже после однозначного поиска по `uid`. Карточка, созданная бухгалтером в 1С с ИНН/КПП уже существующей карточки, тогда никогда не связывалась бы с порталом: каждый `contragent_updated` получал Failed.

### 12. Позиция чтения — смещение группы в Kafka

`СлушатьСообщения` больше не перематывает чтение по `KFK_СмещенияКонсьюмеров`. Источник позиции — смещение, зафиксированное группой в Kafka; регистр — зеркало. При расхождении пишется предупреждение в журнал регистрации (событие консьюмера) и зеркало подтягивается к брокеру до инициализации консьюмера. Повторную обработку уже прочитанных группой сообщений не делаем: от дублей защищает идемпотентность по message id, а явный повтор — `ПовторитьFailed`. Сообщения, которые группу прочитал другой процесс, в эту базу не попадут — это следствие общего имени группы (риск про посторонний участник), а не позиции чтения.

### 13. Привязка ключей и применение снимка — одна транзакция

`ОбработатьСнимокПослеStarted` открывает транзакцию до `ПривязатьВнешниеКлючи` и фиксирует её только после успешного `ПрименитьСнимок<Контур>`. Внутренние транзакции этих функций становятся вложенными. При отказе снимка внутренняя `ОтменитьТранзакцию` помечает всю транзакцию; до внешней отмены код к базе не обращается (обработчик ошибки в `ПрименитьСнимок` работает только со строками), затем внешняя транзакция отменяется, и Failed фиксируется уже вне её. Управляемая блокировка ключей идентичности удерживается до конца применения снимка.

### 14. Договор исходящего снимка обязан иметь организацию с кодом портала

`ПроверитьДоговоры` в режиме отправителя 1С требует `organization` и положительный `organization.id`: входящая обработка того же контура иначе отклонит договор (`REFERENCE_NOT_FOUND` / `DUPLICATE_CONFLICT` по организации). Нарушение роняет сборку тела, публикатор переводит запись в `failed` с путём договора в диагностике; после исправления договора администратор выполняет «Повторить отправку». Проверка входящих снимков портала не меняется.

### 10. Общий код РФ и КЗ

Модуль `KFK_ИсходящиеСнимкиСервер`, подписка, регистр, перечисление и задание одинаковы в обеих поставках, кроме кода контура. Код синхронизируется вручную, как в прошлом change. Сериализатор отличается и живёт в адаптере контура. UUID новых объектов в двух поставках разные: это две независимые сборки расширения.

## Risks / Trade-offs

- [Портал ещё не поддерживает `1.1.0` и исходящие снимки] → исходящий обмен выключен по умолчанию; приём `1.0.*` не меняется; включать после приёмки портала по документу `задание-порталу-исходящие-контрагенты.md`.
- [Счёт или договор, добавленный в 1С после отправки, помечается на удаление следующим полным снимком портала] → это действующее поведение полного снимка; задержка отправки уменьшает окно; ограничение явно указано в задании порталу и в инструкции администратора.
- [Портал не сохранит `uid` карточки или счёта] → поиск по `uid` не сработает, будет дубль карточки или повторный счёт с пометкой на удаление исходного. Поэтому хранение `uid` — обязательное требование к порталу, а приёмка OUT-6 проверяет его на реальном ответе.
- [Портал ответит `updated` раньше, чем истекла задержка] → невозможно: `updated` следует только за полученным снимком.
- [Карточку удалили или пометили на удаление до отправки] → publisher отправляет снимок как есть; пометка удаления в контракт не входит. Если ссылка удалена физически, запись становится `failed` с диагностикой `card_missing`.
- [Регламентное задание на файловой ИБ работает только при живом сеансе] → как и для существующих заданий; отражено в инструкции администратора.
- [Файловая ИБ: фоновые задания одного процесса выполняются по очереди] → установлено живым прогоном 11.11.2026: консьюмер `contragents` работает бесконечным циклом, и консьюмер статусов, запущенный из того же сеанса, не стартует, пока первый не остановится. На файловой ИБ каждый консьюмер запускается в своём процессе (отдельный сеанс или внешнее соединение); задание мониторинга в одном сеансе поднимает только один из них. На клиент-серверной ИБ ограничения нет. До включения в рабочей базе выяснить её тип; для файловой — решить, запускать консьюмеры раздельно или объединить чтение двух топиков в один цикл.
- [Зависание консьюмера `contragents` при старте после перемотки] → воспроизведено 11.11.2026 в КЗ: если смещение в `KFK_СмещенияКонсьюмеров` меньше зафиксированного в Kafka, `СлушатьСообщения` вызывал `УстановитьПозицииЧтения` на старое смещение, и консьюмер, получив раздел, не читал ничего. Исправлено (решение 12).
- [Привязка внешних ключей фиксировалась до применения снимка] → `ПривязатьВнешниеКлючи` писала `KFK_ВнешнийID` (или создавала карточку) в своей транзакции; при отказе снимка ключ оставался. Исправлено (решение 13).
- [В consumer group контура подключился посторонний участник] → 11.11.2026 в `dev.1c.bp.rf` наблюдался второй участник с чужого адреса. Раздел один, поэтому сообщения получает только один участник, и при остановке своего консьюмера их начнёт обрабатывать чужой. Имена групп `<env>.1c.bp.<контур>` должны использоваться только своей базой; ACL на группу — в задании Kafka.
- [Подписка срабатывает на массовой загрузке без `ОбменДанными.Загрузка`] → это осознанно: пользователь выбрал «любое новое, кроме созданных обменом». Нагрузка ограничена размером пачки publisher. Массовые загрузки администратор проводит при выключенном исходящем обмене.
- [В чужом контуре снимок получает Failed по национальной проверке] → принятый исход (решение пользователя от 09.11.2026); портал считает такой Failed ожидаемым.

## Migration Plan

1. Добавить в обе поставки контракт `1.1.0`, валидатор, поиск счёта по `uid` и `ДопустимыеВерсии = 1.0.*;1.1.*`. Прогнать fixtures `1.0.0`: регрессии быть не должно.
2. Добавить регистр, перечисление, подписку, модуль, задание, consumer статусов и настройки с `ИсходящийОбменВключен = Ложь`. Применить расширение в `БП_РФ` и `БП_КЗ` (канон `build/verification/DEPLOY-CFE.md`).
3. Завести в Kafka consumer group `<env>.1c.bp.rf.exchange` / `<env>.1c.bp.kz.exchange` и ACL: WRITE `contragents`, READ `contragents.exchange` для principal 1С.
4. Передать порталу `задание-порталу-исходящие-контрагенты.md`; дождаться поддержки `1.1.0`.
5. Включить исходящий обмен на dev РФ, пройти OUT-1…OUT-9 (портал эмулируется публикацией в Kafka, если реального ещё нет), затем на КЗ.

Откат: `ИсходящийОбменВключен = Ложь` в контуре сразу останавливает регистрацию и публикацию. Уже созданные `KFK_ВнешнийUID` безвредны: входящий поток использует их как обычный ключ. Возврат к прошлой версии расширения допустим. Данные `KFK_ИсходящиеСнимки` при этом теряются вместе с регистром, бизнес-данные не затрагиваются.
